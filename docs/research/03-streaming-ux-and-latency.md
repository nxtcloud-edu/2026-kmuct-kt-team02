# 스트리밍 UX와 체감 지연

> 조사 목적: 규칙 카드를 먼저 띄우고 설명을 스트리밍하는 우리 화면의 시간 목표와 접근성 기준의 근거를 확보한다.
> 조사일 2026-09-20. 출처는 인라인 링크로 표기했다.

## 한 줄 결론

- **10초가 주의력의 경계다.** 우리 전체 상한 20초는 이미 그 경계를 넘는다. 그래서 규칙 카드를 먼저 띄우는 것이 선택이 아니라 필수다.
- **버튼 반응은 200밀리초 안에.** 후속 질문 버튼, 카드 열기, 각주 열기가 여기에 해당한다.
- **스켈레톤이 스피너보다 낫다.** 다만 1초 미만에는 오히려 잡음이다.
- **스트리밍 본문을 스크린리더에 자동 낭독시키지 않는다.** 짧은 상태 메시지만 별도 영역에서 알린다.
- **상태는 색만으로 구분하지 않는다.** 이건 접근성 기준이 명시적으로 요구하는 것이다.

## 1. 응답 시간 임계값

| 기준 | 수치 | 의미 | 자료 |
| --- | --- | --- | --- |
| 즉각 반응으로 느끼는 한계 | 약 0.1초 | 별도 피드백이 필요 없다 | [UX 시간 척도](https://www.nngroup.com/articles/powers-of-10-time-scales-in-ux/) |
| 사고 흐름이 끊기지 않는 한계 | 약 1초 | 지연을 인지하지만 흐름은 유지된다 | 같은 자료 |
| 주의력이 유지되는 한계 | 약 10초 | 넘으면 다른 일을 하려 한다. 남은 시간을 알려 줘야 한다 | 같은 자료 · [10초 이후 이탈 경향 정리](https://www.debugbear.com/blog/web-performance-user-experience) |
| 상호작용 응답 기준 (INP) | 200밀리초 이하가 "좋음", 500밀리초 초과는 "나쁨" | 실제 사용자 75분위 기준 | [INP 최적화](https://web.dev/optimize-inp/?) · [INP 정의](https://web.dev/articles/inp/) |
| AI 도구에도 같은 인간 기준이 적용됨 | 1초 미만이 이상적이고, 불가능하면 진행 표시가 필요하다 | 최근 정리 | [AI 응답 시간](https://www.uxtigers.com/post/ai-response-time) |

**우리 화면에 주는 함의**: 우리 시간 목표를 이 기준에 대응시키면 이렇다.

| 우리 목표 | 대응 기준 | 판단 |
| --- | --- | --- |
| 첫 카드 2초 이내 | 1초 경계를 넘지만 10초 경계 안 | 진행 표시가 필요하다. 스켈레톤으로 대응 |
| 답변 첫 문장 3초 이내 | 같음 | 진행 단계 표시가 필요한 구간 |
| 전체 20초 상한 | 10초 경계를 **넘는다** | 전체 완료를 기다리게 하면 안 된다. 부분 결과를 계속 내보내는 현재 설계가 유일한 해법 |
| 버튼·카드·각주 반응 | 200밀리초 | 여기에 네트워크 호출을 끼워 넣지 않는다. 각주 팝오버는 이미 받아 둔 데이터로 즉시 연다 |

**중요**: 20초 상한은 "20초 동안 아무것도 안 보인다"가 아니라 "그때까지 스트리밍이 끝난다"는 뜻이어야 한다. 카드가 2초에 뜨고, 3초에 첫 문장이 오고, 그 뒤로 계속 무언가가 갱신되면 10초 경계 문제를 피한다.

## 2. 체감 지연 줄이기

| 발견 | 내용 | 자료 |
| --- | --- | --- |
| 스켈레톤 화면을 쓴 쪽이 체감 속도와 탐색 용이성 점수가 더 높았다. 단, 첫 방문에서 기사를 찾는 속도는 스피너 쪽이 빨랐다 | 효과와 예외가 함께 관찰됨 | [스켈레톤 화면의 효과 연구](https://www.researchgate.net/publication/326858669_The_effect_of_skeleton_screens_Users'_perception_of_speed_and_ease_of_navigation) |
| 반복 애니메이션과 스켈레톤을 함께 쓴 조합이 체감 대기 시간을 가장 많이 줄였다. 진행률 표시는 명확성과 투명성 쪽에서 유리하다 | 조합에 따라 다르다 | [피드백 조합과 체감 대기 시간](https://researchdiscovery.drexel.edu/esploro/outputs/graduate/Investigating-the-Effects-of-Different-Feedback/991021889414404721) |
| 스켈레톤이 유용한 구간은 대략 1초에서 10초 사이. 1초 미만에서는 잡음이고 10초를 넘으면 진행률 표시가 더 맞다 | 적용 구간 | [스켈레톤 적용 구간 정리](https://theplusaddons.com/blog/skeleton-loading-screen/) |
| 스켈레톤이 점진적 로딩을 막으면 안 된다. 데이터가 오는 즉시 실제 내용으로 교체해야 한다 | 흔한 오용 | [스켈레톤 화면에 대해 알아야 할 것](https://blog.getadblock.com/what-you-should-know-about-skeleton-screens-a820c45a571a) |

**우리 화면에 주는 함의**: 카드 자리에 스켈레톤 3개를 두는 현재 설계가 근거와 맞다. 목표가 2초이므로 적용 구간(1~10초) 안에 있다. 단 두 가지를 지킨다.

- 카드가 오면 **즉시** 실제 카드로 교체한다. 스켈레톤을 최소 표시 시간 같은 것으로 붙잡아 두지 않는다.
- 데모 모드에서 저장된 결과를 즉시 내보내지 않고 같은 속도감으로 재생하는 이유도 여기 있다. 너무 빠르면 오히려 의심을 산다.

진행 단계 세 개("정책 찾는 중 → 조건 확인 중 → 정리 중")는 진행률 표시에 가까운 역할을 한다. 20초 구간에서는 이게 스켈레톤보다 적합하다.

## 3. LLM 스트리밍 특유의 UX

이 영역은 통제 연구가 드물다. **일부 항목은 근거 약함**으로 표시한다.

| 항목 | 판단 | 근거 성격 |
| --- | --- | --- |
| 첫 조각이 빨리 오는 것이 전체 완료보다 체감에 중요하다 | 1절의 1초·10초 경계와 [AI 응답 시간 권고](https://www.uxtigers.com/post/ai-response-time)로 뒷받침된다 | 간접 근거 |
| 문장 단위로 붙이는 것이 글자 단위보다 읽기 쉽다 | 글자 단위는 읽는 중에 글자가 계속 추가돼 시선이 따라가야 한다. 문장 단위는 읽을 수 있는 덩어리로 도착한다 | 근거 약함, 실무 판단 |
| 스트리밍 중 레이아웃이 흔들리면 읽기가 깨진다 | 시각적 안정성은 핵심 웹 지표에도 별도 항목으로 들어 있다 | [핵심 웹 지표 구성](https://www.corewebvitals.io/improvedcontent/core-web-vitals.html) |

**우리 화면에 주는 함의**: 문장 단위 스트리밍을 유지한다. 그리고 답변 영역 아래에 있는 요소(후속 질문 카드, 관련 질문 칩)가 답변이 길어질 때마다 밀려 내려가는 것을 감수하되, **카드 묶음은 답변 위에 두어 밀리지 않게 한다.** 카드가 답변 아래 있으면 글자가 늘어날 때마다 카드가 움직인다.

각주 번호는 답변 문장 안에 들어간다. 각주 데이터가 답변보다 늦게 오면 번호가 눌리지 않는 구간이 생긴다. 답변 완료 시 각주를 한 번에 연결하는 현재 설계에서는, **각주 번호를 답변 도중에는 눌러도 반응하지 않는 상태로 두지 말고 완료 후 활성화한다.**

## 4. 접근성

| 기준 | 내용 | 자료 |
| --- | --- | --- |
| 보통은 `polite`만 쓴다. 사용자에게 중요하지만 거슬릴 정도로 빈번하지 않은 갱신에 쓴다. 스크린리더는 사용자가 쉴 때 읽는다 | 기본값 | [ARIA 라이브 리전](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions) |
| `assertive`는 읽던 것을 끊는다. 오류나 결정적 피드백처럼 정말 급한 경우에만 | 절제 | [라이브 리전 설명](https://pressbooks.library.torontomu.ca/wafd/chapter/live-regions/) |
| 갱신 중에는 낭독을 막을 수 있고, 다시 읽을 범위를 지정할 수 있다 | 관련 속성 | [aria-live 속성](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live) |
| 라이브 리전은 갱신이 일어나기 **전에** 페이지에 있어야 한다. 짧고 유용한 메시지로 교체한다. 일상적 진행에는 공손한 영역을, 정말 급한 것에만 단호한 영역을 쓴다 | 구현 순서 | [동적 갱신 알림 방법](https://johnkavanagh.co.uk/articles/announcing-dynamic-updates-with-aria-live-regions/) |
| **스트리밍 본문 자체를 자동 낭독 대상으로 삼지 않는다. "응답 생성 중", "응답 완료" 같은 짧은 상태만 별도 요소에서 알린다** | 스트리밍 채팅 UI의 핵심 실천 | [스트리밍 채팅 UI의 스크린리더 알림](https://azukiazusa.dev/en/blog/accessible-streaming-chat-ui/) |

**우리 화면에 주는 함의**: 여기가 우리 기존 설계를 **수정해야 하는 지점**이다.

기존 설계는 "답변 스트리밍 영역을 스크린리더가 읽도록 설정"이라고만 적혀 있었다. 그대로 구현하면 문장이 붙을 때마다 낭독이 끊기고 다시 시작돼 스크린리더 사용자에게는 오히려 읽을 수 없는 화면이 된다.

| 대상 | 어떻게 |
| --- | --- |
| 진행 단계 | 공손한 라이브 리전에서 짧게 알린다. "정책 찾는 중", "조건 확인 중", "정리 중" |
| 답변 본문 | 자동 낭독 대상으로 두지 않는다. 완료 후 사용자가 직접 읽을 수 있게 둔다 |
| 완료 알림 | 공손한 영역에서 "답변 완료. 제도 5개를 찾았어요" 같은 한 줄 |
| 카드 상태 갱신 | 공손한 영역에서 "조건이 갱신됐어요" 정도. 카드마다 알리지 않는다 |
| 오류 | 단호한 영역 또는 경고 역할. 여기서만 끊는다 |
| 라이브 리전 준비 | 갱신 전에 미리 페이지에 둔다 |

색·대비·포커스 기준은 `docs/08-risks-privacy-a11y.md`에 이미 있다. 요지는 상태를 색만으로 구분하지 않고 문구와 아이콘을 함께 쓰는 것, 본문 대비 4.5:1 이상, 모든 조작 요소에 포커스 표시다.

## 5. 결과가 나중에 바뀔 때

우리는 규칙 기반 카드를 먼저 띄우고 AI 판정 후 상태를 갱신한다. 사용자가 이미 읽은 내용이 바뀌는 구조다.

| 위험 | 대응 |
| --- | --- |
| 카드 순서가 바뀌어 사용자가 보던 카드를 잃는다 | 기존 카드는 자리를 유지하고 상태만 바꾼다. 새 카드는 뒤에 추가한다 |
| 바뀐 것을 알아채지 못한다 | 배지를 0.3초 동안 부드럽게 바꾸고 "업데이트됨"을 2초 표시한다. 0.3초는 1절의 즉각 반응 한계보다 길어 변화가 눈에 보이는 시간이다 |
| 바뀐 것이 너무 많아 어수선하다 | 스크린리더에는 카드별로 알리지 않고 한 번만 알린다 (4절) |
| "왜 아까와 다르지"라는 의심 | 상태가 바뀐 이유는 조건 판정표에서 확인할 수 있다. 각주로 원문까지 간다 |

## 우리 화면에 반영할 것

| 발견 | 반영할 규칙 | 화면 위치 |
| --- | --- | --- |
| 10초가 주의력 경계 | 전체 완료를 기다리게 하지 않는다. 카드 2초, 첫 문장 3초, 이후 계속 갱신 | 대화 결과 전체 |
| INP 200밀리초 | 버튼·카드·각주 반응에 네트워크 호출을 끼우지 않는다. 각주는 받아 둔 데이터로 즉시 연다 | 후속 질문 버튼, 카드, 각주 팝오버 |
| 스켈레톤은 1~10초 구간에 유효 | 카드 자리에 스켈레톤 3개. 데이터가 오면 즉시 교체, 최소 표시 시간을 걸지 않는다 | 첫 결과 대기 |
| 진행률 표시가 긴 구간에 적합 | 진행 단계 3개를 쓰고 완료 단계는 체크 표시 | 답변 위 한 줄 |
| 레이아웃 흔들림 | 카드 묶음을 답변 **위**에 둔다 | 대화 결과 |
| 각주 타이밍 | 각주 번호는 답변 완료 후 활성화한다 | 답변 본문 |
| 스트리밍 본문을 자동 낭독하지 않는다 | 진행 단계와 완료만 공손한 영역에서 알린다. 본문은 낭독 대상에서 뺀다 | 답변 영역, 상태 영역 |
| 급한 것만 끊는다 | 오류에만 단호한 알림. 나머지는 공손하게 | 오류 표시 |
| 라이브 리전은 미리 존재해야 한다 | 상태 영역을 처음부터 화면에 둔다 | 대화 결과 |
| 갱신 혼란 | 기존 카드 자리 유지, 상태만 변경, 변경 강조 2초 | 정책 카드 |

## 반영하지 않기로 한 것

| 항목 | 왜 |
| --- | --- |
| 남은 시간 예측 표시 | 단계별 소요가 정책 수와 모델 응답에 따라 크게 흔들려 틀린 예측이 더 나쁘다 |
| 실제 사용자 지표 수집 (INP·LCP 실측) | 하루 안에 측정 도구를 붙일 수 없다. 데모 경로 실측으로 대체한다 |
| 모바일 세부 다듬기 | 발표 시연은 데스크톱 기준. 모바일은 깨지지 않는 수준까지만 |
| 스크린리더 실기기 검증 | 보조기술 수동 테스트가 필요하다. 하루 안에는 못 한다. 기준을 지키는 수준까지만 하고 한계로 밝힌다 |
| 진행률 퍼센트 표시 | 단계 세 개로 충분하고, 퍼센트는 근거 없는 숫자가 된다 |
