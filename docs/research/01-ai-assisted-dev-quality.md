# AI 코딩 품질

> 조사 목적: 5명이 전원 AI 코딩 에이전트로 하루 약 4시간 안에 만드는 조건에서, 품질이 무너지는 지점과 그것을 막는 실천법의 근거를 확보한다.
> 조사일 2026-09-20. 출처는 인라인 링크로 표기했다.

## 한 줄 결론

- **빠르다는 느낌을 믿지 않는다.** 통제 실험에서 체감과 실측이 반대로 나왔다. 진행 상황은 시각(12:00, 14:00)으로 점검한다.
- **AI가 쓴 코드는 기본적으로 취약하다고 가정한다.** 인증·입력 검증·외부 호출이 있는 자리는 사람이 직접 읽는다.
- **의존성 이름을 믿지 않는다.** 에이전트가 제안한 패키지는 실제 존재와 최신 버전을 확인하고 버전을 고정한다.
- **인터페이스를 먼저 못 박고 폴더를 나눈다.** 병렬로 돌릴 때 깨지는 건 코드 품질이 아니라 합의다.
- **한 커밋에 하나의 관심사만.** 커밋이 커지면 리뷰가 아니라 체념이 된다.
- **되돌릴 수 있는 상태를 자주 만든다.** 동작하는 지점마다 커밋해 언제든 그 지점으로 돌아갈 수 있게 한다.

## 1. AI 생성 코드의 알려진 결함

실증 연구는 대체로 "돌아가지만 안전하지 않다"로 수렴한다.

| 발견 | 수치 | 자료 | 연도 |
| --- | --- | --- | --- |
| 공개 저장소의 Copilot 생성 코드 조각에서 보안 약점이 발견됨 | Python 조각 29.5%, JavaScript 조각 24.2% | [GitHub 프로젝트 내 Copilot 생성 코드의 보안 약점](https://arxiv.org/html/2310.02059v4) | 2023~ |
| 여러 모델이 생성한 프로그램 중 취약한 비율 | 최소 62.07% | [대규모 모델 비교 연구](https://arxiv.org/html/2404.18353v2) | 2024 |
| 모델별 차이는 크지 않고 오류 유형이 비슷함 | — | 같은 연구 | 2024 |
| LLM은 코드 생성 중 취약점을 만들기도 하고, 있는 취약점을 놓치기도 하고, 없는 것을 보고하기도 함 | — | [코드 보안 분야 LLM 체계적 문헌 검토](https://arxiv.org/html/2412.15004v4) | 2024~2026 |
| 복잡한 과제에서 기능을 잘못 구현하는 오류가 미묘하게 섞임 | — | [생성 코드 정확성 분석](https://arxiv.org/pdf/2409.19182) | 2024 |

**우리에게 주는 함의**: 우리 서버는 인증 없이 열린 API를 노출한다. 민감정보 마스킹(FR15)과 입력 검증은 에이전트가 쓴 것을 그대로 두지 않고 사람이 읽는다. 세션을 메모리에만 두는 선택이 결과적으로 공격 표면을 줄인다.

## 2. 생산성 효과의 실제 크기

가장 통제가 잘 된 실험의 결과가 직관과 반대다.

| 발견 | 수치 | 자료 | 연도 |
| --- | --- | --- | --- |
| 자기 저장소에서 작업하는 숙련 오픈소스 개발자가 AI 도구를 쓸 때 완료 시간 | 19% 더 **오래** 걸림 | [METR 무작위 대조 실험](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) · [논문](https://arxiv.org/abs/2507.09089) | 2025 |
| 실험 설계 | 16명, 246개 과제, 평균 5년 경험한 성숙한 프로젝트 | 같은 자료 | 2025 |
| 참가자의 사후 인식 | 평균 20% 빨라졌다고 **느낌** | [실험 보도 정리](https://arstechnica.com/ai/2025/07/study-finds-ai-tools-made-open-source-software-developers-19-percent-slower/) | 2025 |
| 사전 기대 | 참가자와 전문가 모두 약 40% 단축을 예상 | [실험 결과 요약](https://infoq.com/news/2025/07/ai-productivity?) | 2025 |
| 후속 | METR이 실험 설계를 변경한다고 공지 (일반화 범위에 유보가 있다는 뜻) | [설계 변경 공지](https://metr.org/blog/2026-02-24-uplift-update/) | 2026 |

**주의**: 이 실험은 자기 코드베이스를 잘 아는 숙련자가 성숙한 저장소에서 작업한 조건이다. 우리 상황(새 저장소, 처음 만드는 코드, 문서가 먼저 있는 상태)은 조건이 다르므로 19%를 그대로 적용할 수 없다. 다만 **체감과 실측이 갈린다는 사실**은 그대로 유효하다.

**우리에게 주는 함의**: "잘 되고 있는 것 같다"를 진행 보고로 쓰지 않는다. 12:00과 14:00에 화면과 응답으로 확인한다. 데모 경로가 끝까지 통과하는지가 유일한 진행 지표다.

## 3. 의존성 환각과 공급망 위험

| 발견 | 수치 | 자료 | 연도 |
| --- | --- | --- | --- |
| 코드 생성 모델이 실제로 없는 패키지 이름을 제안하는 비율 | 상용 모델 5.2%, 오픈소스 모델 21.7% | [USENIX Security '25 결과를 인용한 후속 연구](https://arxiv.org/abs/2605.17062) | 2025~2026 |
| 한 연구 코퍼스에서 확인된 가상 패키지 이름 | 20만 개 이상 | [환각 패키지와 공급망 방어 정리](https://www.digitalapplied.com/blog/slopsquatting-ai-hallucinated-packages-supply-chain-defense) | 2026 |
| 공격 방식 | 공격자가 환각된 이름을 레지스트리에 미리 등록해 공급망을 오염시킴 (슬롭스쿼팅) | [환각 패키지 이름 위험 분석](https://arxiv.org/abs/2608.23897) | 2026 |
| 성격 | 고립된 실수가 아니라 반복되는 패턴 | [언어·모델 간 재현 조사](https://ijirt.org/publishedpaper/IJIRT191660_PAPER.pdf) | 2026 |

**우리에게 주는 함의**: 에이전트가 제안한 패키지를 그대로 설치하지 않는다. 이름이 낯설면 레지스트리에서 실제 존재와 최근 배포일을 확인한다. 버전은 범위가 아니라 정확한 값으로 고정한다. 하루짜리 데모에서 의존성은 최소로 유지한다. UI 라이브러리는 프론트가 10:30까지 **하나만** 정한다.

## 4. 명세 우선과 컨텍스트 관리

명세를 먼저 문서로 확정하는 방식의 효과를 정면으로 측정한 통제 실험은 찾지 못했다. 이 절은 **근거 약함**으로 표시하고, 다만 관련 근거로 장문 컨텍스트 연구를 연결한다.

| 발견 | 내용 | 자료 | 연도 |
| --- | --- | --- | --- |
| 입력 중간에 있는 정보를 모델이 잘 쓰지 못함. 앞과 뒤에 있을 때 성능이 가장 높음 | 위치에 따른 성능 차이 | [장문 컨텍스트 사용 방식 연구](https://arxiv.org/html/2307.03172v1) · [학술지 게재본](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00638/119630) | 2023~2024 |
| 입력이 길어질수록 성능이 떨어짐. 장문 전용 모델도 예외가 아님 | — | 같은 연구 | 2023~2024 |

**우리에게 주는 함의**: KIRO Spec에 넣는 요구사항을 길게 붙이지 않는다. 자기 역할에 필요한 문서만 넣는다(요구사항 + 용어·프로필 + 자기 역할 README). 전체 문서를 다 넣으면 중간이 묻힌다. **제약과 금지 사항은 프롬프트 앞이나 끝에 둔다.**

## 5. 검증 루프

| 실천 | 왜 | 근거 성격 |
| --- | --- | --- |
| 동작하는 지점마다 커밋 | 돌아갈 지점이 없으면 에이전트가 망친 것을 되돌리는 데 시간을 잃는다 | 실무 권고 |
| 화면이나 응답으로 확인 | "구현했다"는 보고와 동작은 다르다. 2절의 인식 격차가 여기서도 나타난다 | 2절 연구 |
| 보안 민감 지점은 사람이 읽기 | 1절 수치대로 생성 코드의 취약 비율이 높다 | 1절 연구 |
| 의존성 이름 확인 | 3절 | 3절 연구 |
| 타입·린트가 있으면 켜 두기 | 되돌리기 비용이 가장 싼 자동 검증 | 실무 권고 |

우리는 테스트 프레임워크를 새로 세우는 대신 **대표 프로필 5개와 평가 케이스(C1~C8, J1~J8)를 회귀 검사로 쓴다.** 이게 4시간 안에 유지 가능한 유일한 검증 루프다.

## 6. 시간 압박 환경에서의 우선순위

이 절은 대부분 실무 권고다. **근거 약함.**

| 실천 | 내용 |
| --- | --- |
| 범위를 미리 잘라 두기 | 무엇을 뺄지 미리 순서로 합의한다. 당일에 논의하면 그 논의로 시간을 쓴다 |
| 기능 동결 | 14:30 이후 새 기능을 넣지 않는다. 동결 없이 발표에 들어가면 마지막 변경이 데모를 깬다 |
| 폴백 우선 | LLM이 실패해도 규칙 결과로 화면이 서는 구조를 먼저 만든다 |
| 백업 경로 | 배포 주소가 안 열릴 때를 대비한 녹화 영상 |

## 본선 당일 실천 규칙

| 언제 | 무엇을 | 왜 |
| --- | --- | --- |
| 09:00~10:30 | 요구사항·용어·인터페이스 문서를 확정하고 각자 Spec 입력으로 넣는다 | 컨텍스트가 갈리면 같은 개념이 다른 이름으로 구현된다 |
| 10:30 | 인터페이스를 못 박는다. 이후 변경은 백엔드B 경유 | 병렬 작업의 유일한 접합점이다 |
| 10:30~ | 의존성은 최소로, 버전은 고정. 낯선 패키지 이름은 확인 | 3절 |
| 수시 | 동작하는 지점마다 작은 커밋 | 되돌릴 지점 확보 |
| 12:00 | 규칙 판정이 돌고, 프론트가 목업으로 카드를 그리고, 세션 생성이 응답하는지 **화면으로** 확인 | 2절의 인식 격차 |
| 12:00 | 스트리밍이 교차 출처에서 실제로 뚫리는지 확인 | 프론트가 S3에 올라가므로 |
| 13:00~14:30 | AI 호출을 일부러 끊고 카드가 남는지 확인 | 폴백이 설계로만 존재하지 않게 |
| 14:00 | 데모 경로가 끝까지 한 번 통과하는지 확인 | 통과 못 하면 이 시점에 범위를 줄인다 |
| 14:30 | 기능 동결. 이후 버그 수정만 | 마지막 변경이 데모를 깨는 것을 막는다 |
| 14:30~15:00 | 배포 주소에서 데모 경로 재확인, 백업 영상 녹화 | 배포 캐시와 현장 네트워크 대비 |

## 에이전트를 병렬로 쓸 때의 규칙

| 나눠도 되는 작업 | 나누면 위험한 작업 | 이유 |
| --- | --- | --- |
| 서로 다른 폴더의 독립 모듈 | 같은 파일을 동시에 고치는 작업 | 충돌을 사람이 손으로 풀어야 한다 |
| 정책 데이터 수집·검수 (건별로 분할) | 인터페이스·공용 타입 정의 | 두 에이전트가 각자 이름을 지으면 통합에서 깨진다 |
| 평가 케이스 작성, 문서 정리 | 정렬·판정 규칙처럼 여러 모듈이 공유하는 규칙 | 정의가 갈리면 결과가 갈린다 |
| 화면 단위 구현 (카드, 상세 패널, 팝오버) | 전역 상태 구조 설계 | 나중에 합칠 수 없다 |
| 조사·리서치 | 커밋과 머지 | 한 사람(백엔드B)만 합친다 |

**병렬로 돌릴 때 반드시 같이 주는 것**: 고정 값 목록, 필드 이름 규칙, 소유 폴더 경계, 그 작업이 건드리면 안 되는 파일. 이게 없으면 각 에이전트가 자기 가정으로 채운다.

## 하지 말 것

| 흔한 유혹 | 왜 위험한가 | 대신 할 것 |
| --- | --- | --- |
| "일단 다 만들고 나중에 정리" | 정리 시간이 오지 않는다. 14:30에 동결된다 | P0만 만들고 멈춘다 |
| 에이전트에게 저장소 전체를 맡기기 | 남의 폴더를 고쳐 통합을 깬다 | 작업 범위를 폴더로 못 박아 준다 |
| 남의 코드를 지나가며 리팩터링 | 소유자가 모르는 변경이 생긴다 | 소유자에게 말하고 PR로 |
| 커밋을 한 번에 몰아서 | 리뷰도 되돌리기도 불가능해진다 | 관심사 하나마다 커밋 |
| 잘 되는 것 같으니 그냥 진행 | 체감과 실측이 갈린다 (2절) | 화면과 응답으로 확인 |
| 인터페이스를 조금만 바꾸기 | 조금이 아니다. 다섯 명이 멈춘다 | 백엔드B에게 알리고 전원 공지 |
| 데모 직전 재배포 | 캐시로 예전 화면이 뜨거나 새 버그가 들어온다 | 동결 후에는 버그 수정만, 올린 뒤 경로 재확인 |
