# API 서버와 통합 (담당: 백엔드B)

> 출처: 역할별 설계서 4장. **API 상세 명세는 `../docs/03-api-contract.md`가 기준이다.** 이 문서는 그 명세를 복제하지 않고, 통합·조율·운영 관점만 다룬다.
> 본선 당일 오전(09:00~10:30)에 `docs/02-requirements-ears.md` + `docs/01-glossary-profile.md` + 이 파일을 KIRO Spec 요구사항 입력으로 쓴다.
> 본선 전에는 코드를 작성하지 않는다. 이 문서도 글과 표로만 되어 있다.

## 1. 목표

네 사람이 따로 만든 모듈(규칙 엔진, 메시지 해석, 예외 조건 판정, 답변 작성)을 하나의 흐름으로 묶는 것이 서버의 일이다.
그리고 더 중요한 목표는 **어떤 모듈이 실패해도 사용자 화면이 멈추지 않게** 하는 것이다.
AI 세 갈래 중 무엇이 늦거나 깨지더라도 사용자는 규칙 기반 정책 카드를 이미 보고 있어야 한다. 설명이 빠질 수는 있지만 화면이 비어서는 안 된다.

여기에 배포와 통합 일정 관리가 붙는다. 통합 시각을 정하고 그 시각에 실제로 합치는 사람이 백엔드B다.

| 하지 않는 것 | 담당 |
| --- | --- |
| 규칙 조건 판정, D-day 계산, 정렬 | 백엔드A |
| 답변 문장 생성, 후속 질문 문구 | AI A |
| 예외 조건 판정, 인용 검증 기준 | AI B |
| 화면과 사용자에게 보이는 문구 | 프론트 |

서버는 판정을 새로 만들지 않는다. 규칙 결과와 AI 결과를 **합산해 상태를 확정하는 역할만** 한다.
서버가 조건의 충족 여부를 스스로 해석하기 시작하면 판정 근거가 두 곳으로 갈라져 통합 때 어긋난다.

## 3. 모듈 조립 순서

`../docs/03-api-contract.md` 9장의 13단계가 기준이다. 아래는 같은 순서를 **누구의 산출물을 붙이는지**와 **그 단계가 실패했을 때 무엇을 보내는지**로 다시 정리한 것이다.

| 단계 | 하는 일 | 누가 만든 것을 붙이는가 | 이 단계가 실패하면 |
| --- | --- | --- | --- |
| 1 | 민감정보 마스킹 | 백엔드B (서버 자체) | 실패 개념 없음. 가릴 게 없으면 그냥 통과 |
| 2 | 진행 단계 "정책 찾는 중" 알림 | 백엔드B | 이벤트만 빠지고 진행. 사용자는 진행 표시 없이 결과를 받음 |
| 3 | 메시지 해석 | AI A | 프로필 변경 없이 다음 단계로. 기존 프로필로 계속 진행 |
| 4 | 범위 밖·잡담 처리 후 종료 | AI A | 짧은 답변을 못 만들면 `error`(답변 실패) 후 `done` |
| 5 | 규칙 재계산, 후보 선정 | 백엔드A (규칙 엔진) | **대체 없음.** 카드를 만들 수 없다. `error`(서버 오류) 후 `done` |
| 6 | 진행 단계 "조건 확인 중" 알림 | 백엔드B | 이벤트만 빠지고 진행 |
| 7 | 예외 조건 판정 (후보별 동시) | AI B | 해당 정책의 예외 조건 전체를 `unknown`으로 두고 진행 |
| 8 | 인용 검증, 상태 확정 | AI B(검증 기준) + 백엔드B(합산) | 검증 실패한 조건은 `unknown`으로 내리고 발췌를 비움 |
| 9 | 진행 단계 "정리 중" 알림 | 백엔드B | 이벤트만 빠지고 진행 |
| 10 | 답변 작성 | AI A | `error`(답변 실패) 보내고 카드는 유지 |
| 11 | 후속 질문 선택 | AI A(로직·문구) + 백엔드B(세션 이력 제공) | 후속 질문 없이 종료. 화면에 질문 카드만 안 뜸 |
| 12 | 관련 질문 칩 (P1) | AI A | 생략. P1이라 빠져도 무방 |
| 13 | 종료 알림 | 백엔드B | 보내지 못하면 입력창이 잠긴 채로 남는다. 어떤 경우에도 반드시 보낸다 |

조율에서 놓치면 안 되는 네 가지:

**규칙 기반 정책 목록을 AI를 기다리지 않고 먼저 보낸다.** 5단계의 결과를 그 자리에서 내보내고, 7·8단계가 끝난 뒤 같은 목록을 한 번 더 갱신해서 보낸다. 이것이 FR04(답을 먼저 주고 설명을 나중에)의 구현 지점이다. 5단계 결과를 AI와 함께 묶어 한 번에 보내면 요구사항이 깨진다.

**판정 상태는 서버가 확정한다.** 규칙 조건 결과와 AI 조건 결과를 합쳐 `likely`/`check`/`unlikely` 중 하나로 정한다. 결정 규칙은 `../docs/01-glossary-profile.md` 4장에 있고, 서버는 그 규칙을 그대로 적용한다. AI가 답변 문장에서 상태를 다르게 말해도 화면에 표시되는 상태는 서버가 정한 값이다.

**규칙 조건과 AI 조건이 같은 내용을 다르게 판정하면 규칙 조건을 따른다.** `../docs/05-interfaces.md` 6장의 충돌 기준이다. 데이터 필드로 기계적으로 비교한 결과가 원문 해석보다 신뢰도가 높다.

**후속 질문 답변(버튼)이 들어오면 메시지 해석 단계를 건너뛴다.** 항목 이름과 값이 이미 정해져서 오기 때문에 의도를 다시 해석할 필요가 없다. 값을 바로 프로필에 넣고 5단계로 간다. 이 경로로 3초를 절약한다.

## 4. 시간 예산과 실패 시 대체

| 상황 | 처리 | 사용자가 보는 것 |
| --- | --- | --- |
| 메시지 해석이 3초를 넘김 | 프로필 변경 없이 다음 단계로 진행 | 프로필 바가 그대로. 카드와 답변은 정상 표시 |
| 예외 조건 판정이 정책당 8초를 넘김 | 그 정책의 예외 조건 전체를 `unknown`으로 두고 진행 | 그 카드만 미확인 조건이 늘어남. 다른 카드는 정상 |
| 예외 조건 판정 결과 형식이 깨짐 | 한 번 재시도. 또 실패하면 전체 `unknown` | 위와 같음 |
| 답변 작성 실패 | 오류 이벤트(답변 실패) 발행, 카드는 그대로 둠 | 카드는 남고 설명 자리에 오류 문구와 다시 시도 버튼 |
| 전체 20초를 넘김 | 그때까지 모인 결과로 종료 알림 | 답변이 중간에 끊긴 상태로 마무리. 카드는 남음 |
| 규칙 엔진 실패 | **대체 없음** | 카드를 그릴 수 없다. 서버 오류 문구만 |

규칙 엔진은 대체 경로가 없는 유일한 모듈이다. 그래서 **가장 먼저 동작을 확인해야 하는 모듈**이다. 12:00 점검에서 규칙 판정이 돌지 않으면 다른 무엇을 미뤄도 이것부터 살린다.

오류 이벤트를 보낸 경우에도 종료 이벤트는 반드시 보낸다. 종료를 못 보내면 프론트는 입력창을 다시 열지 못하고, 사용자 입장에서는 화면이 멈춘 것과 같다.

모든 실패 경로의 공통 원칙은 하나다. **카드는 남기고 설명만 포기한다.** 어느 단계에서 무엇이 실패해도 이 원칙이 우선한다.

오류 코드와 사용자 문구는 `../docs/03-api-contract.md` 10장에 있다. 서버는 코드를, 프론트는 문구를 담당한다.

## 5. 세션 / 마스킹 / 기록

| 영역 | 핵심 | 상세 |
| --- | --- | --- |
| 세션 | 서버 메모리에만 보관. 데이터베이스를 쓰지 않는다. 30분 비활성 시 폐기 | `../docs/03-api-contract.md` 11장 |
| 보관 내용 | 프로필, 물어본 항목, 건너뛴 항목, 최근 대화 6턴, 현재 표시 중인 정책 목록 | 같은 문서 11장 |
| 기록 제외 | 사용자 메시지 원문과 프로필은 기록하지 않는다 | 같은 문서 11장 |
| 마스킹 | 주민등록번호·계좌번호·전화번호로 보이는 형태를 가리고 안내를 띄운다 | 같은 문서 12장 |
| 마스킹 값 처리 | 가린 값은 AI 요청에도, 기록에도 남기지 않는다 | 같은 문서 12장 |
| 기록 항목 | 단계별 소요 시간, 인용 검증에서 제거된 발췌 수, AI 실패·시간 초과 건수 | 같은 문서 13장 |

데이터베이스를 쓰지 않는 선택은 시간 절약이 목적이지만 결과적으로 개인정보 보관 위험도 줄인다. 4시간 안에 만드는 데모에서 저장소를 붙이면 설정과 배포에서 시간을 잃고, 얻는 것은 새로고침 후 복원 정도다.

마스킹은 값이 AI로 나가기 **전에** 해야 의미가 있다. 순서상 처리의 가장 앞 단계에 두는 이유다. 판단 기준은 명세 문서의 표를 그대로 쓴다. 예를 들어 주민등록번호는 숫자 여섯 자리 다음에 하이픈 또는 공백이 오고 그 다음 숫자 일곱 자리가 이어지는 형태다.

**건너뛴 항목을 세션에 기록해 같은 질문을 다시 하지 않게 하는 것은 서버 책임이다.** 후속 질문을 고르는 로직은 AI A가 만들지만, 어떤 항목을 이미 물었고 어떤 항목을 사용자가 건너뛰었는지는 세션이 알고 있어야 한다. 서버가 그 목록을 넘기지 않으면 같은 질문이 반복되고, 대화가 취조처럼 느껴진다.

## 6. 저장소와 통합 운영

| 항목 | 결정 |
| --- | --- |
| 저장소 구성 | 하나의 저장소에 프론트, 서버, 규칙 엔진, AI 모듈, 정책 데이터 폴더를 나눈다 |
| 브랜치 | 역할별 브랜치에서 작업하고 통합 대상 브랜치로 모은다 (`../CONTRIBUTING.md` 2장) |
| 통합 시각 | 12:00과 14:00, 두 번 |
| 발표용 브랜치 머지 | 백엔드B만 한다 |
| 기능 동결 이후 | 14:30 이후 발표용 브랜치에는 버그 수정만 올린다 |
| 인터페이스 문서 변경 | `docs/05-interfaces.md`를 건드리는 PR은 백엔드B 확인 필수 |
| 충돌 | 자기 역할 폴더 밖에서 난 충돌은 백엔드B가 해결한다 |

본선 당일 코드를 올리기 시작할 때 백엔드B가 **무시 목록을 저장소에 추가한다.** 들어갈 것은 의존성 폴더, 빌드 산출물, 환경 변수 파일, 대표 프로필 정답셋, 설문 원본이다. 이 작업을 10:30 직후에 해야 한다. 한 사람이라도 의존성 폴더를 올려버리면 그 뒤 모든 통합에서 충돌이 난다.

### 중간 점검 기준

| 시각 | 여기까지 되어 있어야 한다 | 안 됐으면 |
| --- | --- | --- |
| 12:00 | 규칙 판정이 돌고, 프론트가 목업으로 카드를 그리고, 세션 생성이 응답한다 | 범위를 줄인다 (`../docs/00-overview.md`의 빼는 순서) |
| 14:00 | 데모 경로가 끝까지 한 번 통과한다 (각주·후속 질문·상세 포함) | P1 항목을 전부 버리고 데모 경로만 남긴다 |
| 14:30 | 기능 동결 | 미완성 기능은 되돌리고 동작하는 상태를 남긴다 |

점검의 목적은 진행률 확인이 아니라 **범위를 줄일지 결정하는 것**이다. 기준에 미달했는데 그냥 넘어가면 14:30에 아무것도 동작하지 않는 상태가 된다.

## 7. 데모 안정성

| 항목 | 내용 | 시각 |
| --- | --- | --- |
| 데모 모드 | 데모 경로 입력에 대한 최종 결과를 저장해 두고, 같은 입력이 오면 저장된 결과를 같은 속도감으로 스트리밍한다. 켜고 끄는 방법은 팀만 안다 | 13:00 이후 준비 |
| 응답 시간 측정 | 14:30~15:00 데모 경로를 5회 실행해 응답 시간을 기록한다 | 14:30~15:00 |
| 백업 영상 | 데모 전체를 화면 녹화해 영상으로 확보한다 | 14:30~15:00 |
| 사전 설치 | 현장 네트워크 혼잡에 대비해 필요한 설치는 미리 끝낸다 | 본선 전 |

데모 모드는 발표 도중 AI 호출이 느려지거나 실패하는 상황에 대한 보험이다. 같은 속도감으로 재생하는 게 중요하다. 저장된 결과를 즉시 내보내면 실제 동작과 다르게 보여서 오히려 의심을 산다.

백업 영상은 배포 주소가 현장에서 안 열릴 때 쓴다. 영상까지 확보하면 발표 실패 경로가 사실상 사라진다.

## 8. 프론트 지원

**프론트가 1명이라 가장 큰 병목이다.** 화면은 온보딩 폼부터 대화, 스트리밍 표시, 정책 카드, 각주 팝오버, 상세 패널, 체크리스트, 접근성까지 범위가 넓다. 그래서 백엔드B는 API 작업이 끝나는 대로 프론트의 연결 작업을 직접 맡는다. 13:00 이후 일정에 이 지원이 들어가 있다.

| 항목 | 방법 |
| --- | --- |
| API 확정 시각 | 10:30. 이후 바꾸지 않는다. 꼭 바꿔야 하면 전원 공지 |
| 프론트의 선행 작업 | 확정된 API 문서만 보고 목업 데이터를 만들어 화면을 먼저 완성 |
| 연결 작업 분담 | 서버 쪽 작업이 끝나면 백엔드B가 프론트 폴더에서 연결 작업 지원 |
| 오류 문구 | 서버는 코드를, 프론트는 문구를 담당 |

10:30에 API를 확정하는 이유는 프론트가 서버를 기다리지 않게 하려는 것이다. 서버가 응답을 내놓는 시점은 빨라도 10:30이다. 그 한 시간을 프론트가 대기로 쓰면 회복할 수 없다.

## 9. 사전 준비 체크리스트

| 준비할 것 | 확인 방법 |
| --- | --- |
| API·이벤트·오류 문구를 프론트와 함께 확인 | 프론트가 문서만 보고 목업을 만들 수 있는지 직접 물어본다 |
| KIRO Spec에 넣을 순서 정리 | 요구사항 문서, 용어·프로필 문서, 역할별 문서를 어떤 순서로 넣을지 미리 적어 둔다 |
| 캠프 제공 환경 확인 | 쓸 수 있는 LLM 종류, 호출 한도, 배포 가능한 서비스, 팀원 계정 공유 방식 |
| 설문 원본 시트 공개 범위 제한 | 팀 내부만 접근 가능하게 바꾸고 공개 문서에는 비식별 요약만 |
| 서버 언어·런타임·배포 대상 결정 | 캠프 환경 확인 후 10:30까지 확정 |

캠프 제공 환경 확인이 가장 먼저다. 호출 한도를 모르는 상태로 들어가면 후보별 동시 판정이 한도에 걸려 7단계가 전부 미확인으로 떨어질 수 있다. 배포 가능한 서비스도 미리 알아야 10:30에 배포 대상을 정할 수 있다.

## 10. 완료 기준

| 기준 | 확인 방법 |
| --- | --- |
| 데모 경로 전체가 한 번에 동작 | 온보딩부터 각주·후속 질문·상세까지 끊김 없이 통과 |
| AI 판정을 일부러 끊어도 카드가 표시 | 예외 조건 판정을 막아 두고 규칙 결과로 카드가 나오는지 확인 |
| 데모 모드 동작, 백업 영상 확보 | 데모 모드로 5회 실행, 녹화 파일 재생 확인 |
| 배포 주소에서 팀 외부 3명이 사용 가능 | 외부 3명에게 주소를 주고 온보딩부터 끝까지 시켜 본다 |
| 출처·확인일 없는 정책이 응답에 섞이지 않음 | 응답에 들어간 정책 전부에 원문 주소와 최종 확인일이 있는지 확인 (FR12) |

두 번째 기준이 이 문서의 목표와 직결된다. AI를 끊고도 화면이 살아 있는지 확인하지 않으면 실패 대체 경로는 설계로만 존재하는 것이다. 13:00~14:30 사이에 한 번은 반드시 실제로 끊어 보고 확인한다.

## 11. 프론트가 S3에 올라간다는 전제

프론트는 캠프에서 제공하는 **S3**에 정적 파일로 올라간다. 서버와 다른 오리진이 된다. 서버 쪽에서 챙길 것이 생긴다.

| 항목 | 무엇을 해야 하는가 | 왜 |
| --- | --- | --- |
| 교차 출처 허용 | 프론트 주소를 허용 오리진으로 등록한다. 와일드카드로 열지 않는다 | 등록하지 않으면 브라우저가 모든 요청을 막는다. 화면이 완성돼도 데이터가 오지 않는다 |
| 스트리밍도 같은 규칙을 받는다 | 스트리밍 응답에도 교차 출처 허용이 적용되는지 실제로 확인한다 | 일반 요청은 되는데 스트리밍만 막히는 경우가 흔하다. 12:00 통합 때 확인한다 |
| 사전 요청 처리 | 본문이 있는 요청 전에 브라우저가 먼저 확인 요청을 보낸다. 이것도 응답해야 한다 | 폼 제출과 대화 요청이 전부 여기에 걸린다 |
| 프로토콜 일치 | 프론트 페이지와 API의 프로토콜을 맞춘다 | 페이지가 보안 연결인데 API가 아니면 브라우저가 차단한다. 배포 직전에 발견하면 손쓸 시간이 없다 |
| 주소 고정 | 서버 주소를 10:30에 확정해 프론트에 준다. 이후 바꾸지 않는다 | 프론트는 주소를 설정 파일에 넣어 두고 읽는다. 주소가 바뀌면 프론트가 다시 올려야 한다 |
| 인증은 없다 | 세션 번호만으로 식별한다. 쿠키를 쓰지 않는다 | 교차 출처에서 쿠키를 다루면 설정이 늘어난다. 개인 식별 정보를 받지 않으므로 필요도 없다 |

**서버는 네트워크에 열린 API를 인증 없이 노출한다.** 개인 식별 정보를 받지 않고 세션이 메모리에만 있어 유출 대상이 적지만,
누구나 호출할 수 있다는 뜻이다. 해커톤 데모 범위에서는 받아들이고, 대신 이 점을 발표에서 한계로 밝힌다.
호출 한도가 걱정되면 세션당 요청 수를 제한하는 정도만 둔다.

## 12. 미확정

| 항목 | 누가 | 언제까지 |
| --- | --- | --- |
| 파이썬 웹 프레임워크 (스트리밍 응답을 다룰 수 있는 것) | 백엔드B | 10:30 |
| 서버 배포 대상 (프론트는 S3로 확정) | 백엔드B (캠프 제공 환경 확인 후) | 10:30 |
| 사용할 LLM과 호출 방식 | 백엔드B (캠프 제공 환경 확인 후) | 10:30 |
| 프론트 주소와 API 주소, 프로토콜 일치 | 백엔드B + 프론트 | 10:30 |

**서버 언어는 파이썬으로 확정됐다.** 규칙 엔진과 AI 모듈도 파이썬이라 세 부분이 같은 프로세스 안에서 함수 호출로 연결된다.
따라오는 것들이 있다.

| 항목 | 내용 |
| --- | --- |
| 모듈 간 연결 | 규칙 엔진과 AI 모듈을 별도 서비스로 띄우지 않는다. 같은 애플리케이션 안에서 불러 쓴다. 4시간 안에 서비스를 쪼개면 통합에서 시간을 잃는다 |
| 이름 변환 | 서버·규칙·AI 사이에는 변환이 없다. 문서의 snake_case 이름을 그대로 쓴다 |
| 경계 유지 | 같은 언어라 경계가 흐려지기 쉽다. **규칙 판정 로직을 서버 쪽에 복사하지 않는다.** 판정은 `rules/`에만 있고 서버는 결과를 받아 합산만 한다 |
| 후보별 동시 판정 | 예외 조건 판정을 정책별로 동시에 보낸다. 프레임워크를 고를 때 이걸 다룰 수 있는지 확인한다 |
| 스트리밍 | 대화 응답을 흘려보낼 수 있어야 한다. 프레임워크 선택의 첫 기준이다 |
| 프레임워크 선택 기준 | 스트리밍 응답, 동시 호출, 교차 출처 설정, 이 셋을 다룰 수 있고 백엔드B가 이미 아는 것 |
| 의존성 | 최소로. 버전을 정확히 고정한다. 가상환경은 저장소에 올리지 않는다 |

추측으로 미리 채우지 않는다. 현장에서 쓸 수 없는 것을 전제로 설계하면 10:30에 전부 다시 정해야 한다.
