## 1. 목표

필드로 표현할 수 없는 예외 조건을 **공고 원문 근거로만** 판정하고, 원문에 없는 근거는 한 글자도 화면에 나가지 않게 막는 것.

이 역할이 제품의 신뢰를 지탱한다. 발표에서 "AI가 지어낸 조건이 0건"이라고 말할 수 있는지가 여기서 갈린다. 인용을 붙이게 하는 지시만으로는 근거성이 보장되지 않는다는 것이 이 분야의 출발점이다(`../../docs/research/02-grounding-and-citation.md` 1절).

## 2. 담당 범위

예외 조건 판정, 원문 발췌, 인용 검증, 예외 조건의 조건부 문장, 체크리스트 추출, 근거 없는 조건 점검, 지표 정리.

## 3. 판정 대상

| 구분 | 내용 |
| --- | --- |
| 판정하는 것 | 정책의 `exceptions_text`에 있는 문장형 조건만 |
| 판정하지 않는 것 | 나이, 지역, 신분, 소득 %, 추가 항목, 마감. 규칙 엔진 몫이다. 겹쳐도 다시 판정하지 않는다 |
| 판정 단위 | 정책 하나씩. 후보 정책들을 동시에 |
| 충돌 시 | 규칙 조건과 결과가 다르면 **규칙 조건을 따른다** |

정책별로 따로 판정하는 이유는 긴 입력에서 중간 정보가 묻히기 때문이다(`../../docs/research/02-grounding-and-citation.md` 5절). 호출 한도 때문에 묶어야 한다면 **3건까지**만 묶고, 지켜야 할 규칙을 프롬프트 앞과 끝에 두 번 둔다.

## 4. 판정 기준

| 결과 | 기준 | 예 |
| --- | --- | --- |
| `met` | 프로필에 명시된 값으로 조건을 만족하는 것이 분명함 | "재학생 또는 휴학생" + 사용자 휴학 |
| `unmet` | 프로필에 명시된 값이 제외 대상에 분명히 해당함 | "휴학생 제외" + 사용자 휴학 |
| `unknown` | 프로필에 해당 정보가 없음, 원문 표현이 모호함("등", "그 밖에"), 판단에 외부 정보가 필요함 | "타 지원금 수혜자 제외" + 정보 없음 |

### 미충족은 분명할 때만

**조금이라도 애매하면 미확인이다.** 이 비대칭이 이 역할의 핵심 판단이다.

| 오판 | 사용자에게 일어나는 일 | 비용 |
| --- | --- | --- |
| `unmet` 오판 | 받을 수 있는 제도가 "어려울 수 있어요"로 접힌 영역에 들어간다. 사용자는 그 제도를 포기한다 | 크다. 되돌릴 수 없다 |
| `unknown` 오판 | 질문이 하나 늘거나 조건부 문장이 하나 붙는다 | 작다 |

그래서 `unmet`은 프로필에 **명시된 값**으로 제외 대상에 해당하는 것이 분명할 때만 쓴다.

### 추정 금지

사용자가 말하지 않은 것을 상식으로 추정하지 않는다.

| 금지되는 추론 | 왜 |
| --- | --- |
| 대학생이니 소득이 낮을 것이다 | 프로필에 없는 값을 만든다 |
| 서울에 산다니 서울 소재 대학일 것이다 | 거주지와 학교 소재지는 다른 정보다 |
| 재학생이니 다른 지원은 안 받을 것이다 | 근거가 없다 |
| 휴학이라고 했으니 구직 중일 것이다 | 근거가 없다 |

후보 정책의 원문만 컨텍스트에 넣고, 원문에 없는 조건을 만들지 않는다. 출력은 정해진 형식으로 강제한다.

## 5. 판정 결과 항목

| 항목 | 기준 |
| --- | --- |
| 조건 요약 | 20자 이내 명사형. 예: 타 청년 지원금 중복 불가 |
| 결과 | `met`, `unmet`, `unknown` |
| 발췌 | 원문의 연속된 부분 그대로. 10~150자. 조건당 1개 |
| 필요한 추가 항목 | `unknown`일 때만. 프로필 추가 항목 이름 또는 "공고 확인 필요" |

항목을 얕고 적게 유지하는 것은 의도적이다. 형식 강제가 강할수록 추론 품질이 떨어질 수 있고, 목록과 복합 객체가 들어가면 난도가 올라간다(`../../docs/research/02-grounding-and-citation.md` 3절).

엄격한 스키마 강제 모드는 모든 속성을 필수로 요구하는 경우가 있다. "필요한 추가 항목"은 **항목을 빼는 방식이 아니라 빈 값을 허용하는 방식**으로 설계한다(`../../docs/research/04-llm-api-operations.md` 1절).

## 6. 인용 검증

이게 이 역할의 핵심 안전장치다. **검증은 AI가 아니라 로직으로 한다.**

| 단계 | 기준 |
| --- | --- |
| 정리 | 발췌와 `raw_text` 모두 아래 정규화 규칙으로 맞춘다 |
| 대조 | 정리된 발췌가 정리된 `raw_text` 안에 그대로 들어 있는지 확인 |
| 통과 | **원문에서 되찾은 구간으로 발췌를 교체**한다 |
| 실패 | 그 조건을 `unknown`으로 바꾸고, 발췌와 조건 요약을 화면에 내보내지 않는다. **제거 건수를 기록한다** |

규칙 조건의 근거 문장(`condition_sources`)도 같은 방식으로 한 번 검증한다. 백엔드A가 스프레드시트에 손으로 옮긴 문장에도 오차가 생길 수 있다.

### 정규화 규칙 (macOS · Windows 혼용 대응)

"줄바꿈과 연속 공백을 공백 하나로" 만으로는 **검증이 전건 실패한다.** 사람 눈에 같아 보이는 문자열이 코드에서 다른 경우가 세 층으로 존재한다. 순서대로 적용한다.

| 순서 | 처리 | 막는 문제 |
| --- | --- | --- |
| 1 | 유니코드 **NFC** 정규화 | macOS는 한글을 자모 분해형(NFD)으로 넘기는 경로가 많다(파일명, 클립보드, 일부 브라우저 복사). Windows는 완성형(NFC). "휴학"이 NFC 2자 / NFD 4자가 되어 포함 검사가 **무조건** 실패한다 |
| 2 | 제로폭 문자 제거 — `U+FEFF`(BOM), `U+200B/C/D`, `U+2060`, `U+00AD` | Windows Excel의 UTF-8 저장은 선두에 BOM을 붙인다. 웹 공고 복사에는 제로폭 공백이 섞인다 |
| 3 | 공백류를 공백 하나로 — `\t \n \r \v \f`, `U+00A0`(NBSP), `U+3000`(전각), `U+2000~200A`, `U+202F`, `U+205F`, `U+1680` | CRLF/LF 차이, HTML `&nbsp;` 복붙, 한글 공고의 전각 공백 들여쓰기 |
| 4 | 연속 공백을 하나로 접기 | AI가 줄바꿈을 공백으로 바꿔 인용하는 경우 |
| 5 | 앞뒤 공백 제거 | |

**문장 부호는 건드리지 않는다.** 대시·따옴표 종류를 통일하면 근거의 내용을 바꾸게 된다. 정규화는 보이지 않는 차이만 흡수한다.

`.gitattributes`가 저장소 텍스트를 LF로 강제해 1차 방어를 한다. 다만 스프레드시트 붙여넣기나 API 응답은 git을 거치지 않으므로 런타임 정규화가 최종 방어선이다. 둘 다 있어야 한다.

### 원문 되찾기 (원문 우선 원칙)

정규화는 비교에만 쓴다. 검증을 통과하면 정규화 위치를 원문 위치로 되돌려 **원문에서 실제 구간을 꺼내 발췌를 교체한다.** AI가 공백을 다르게 쓴 발췌를 보내도 사용자가 보는 문장은 항상 공고 원문 쪽이다 (`../../docs/05-interfaces.md` 6장).

### 발췌 길이 처리

- 10자 미만: 실패. 근거로 쓸 수 없고 아무 데나 매칭된다
- 150자 초과: **실패로 보지 않고 앞 150자로 자른 뒤 검증.** 포함된 문자열의 앞부분도 포함되므로 안전하고, 길이 때문에 맞는 판정을 버리지 않는다. 자른 뒤에도 원문에 없으면 그대로 실패

### 실패 사유 코드 (지표용)

`empty_excerpt` · `empty_raw` · `too_short` · `not_found`

### 데이터 불변식: `exceptions_text` ⊂ `raw_text`

판정 입력은 `exceptions_text`인데 대조 대상은 `raw_text`다. `exceptions_text`를 요약하거나 고쳐 적으면 그 정책의 **모든 발췌가 `not_found`로 떨어진다.** 정책 데이터를 적재할 때 `raw_text_covers()`로 미리 걸러야 한다. **백엔드A에 공유해야 하는 사항.**

### 통과율이 낮게 나오면

문자열 대조는 모델이 문장을 미세하게 바꿔 쓰거나 줄임표를 넣으면 통과하지 못한다. **그건 의도된 동작이다.**

| 하지 말 것 | 대신 할 것 |
| --- | --- |
| 부분 일치나 유사도로 검증을 느슨하게 풀기 | 발췌 요구를 더 좁힌다. 연속 구간, 10~150자, 조건당 하나 |
| 검증을 건너뛰는 예외를 두기 | 통과하지 못한 조건은 미확인으로 두고 넘어간다 |
| 모델에게 검증을 맡기기 | 검증 대상과 같은 종류의 실패를 공유한다 |

표가 섞인 원문은 대조가 자주 깨진다. `raw_text` 단계에서 표를 한 줄씩 풀어 두는 것이 대비다(`../../docs/04-data-schema.md` 2장). 통과율이 계속 낮으면 백엔드A와 `raw_text` 형태를 먼저 본다.

문자열 대조를 고른 이유는 세 가지다. 우리가 보여주는 것이 요약이 아니라 **원문 발췌 그 자체**라서 의미 일치 판정이 필요하지 않고, 판정 주체가 로직이라 "왜 이 조건이 사라졌나"를 즉시 설명할 수 있고, 실패 방향이 안전하다(미확인으로 강등).

## 7. 조건부 문장

| 미확인 원인 | 문장 형태 |
| --- | --- |
| 소득 | 가구 소득이 기준 중위소득 n% 이하라면 신청 가능해요 |
| 추가 항목 | (조건절 문구 표에서 고름) + 신청 가능해요 |
| 예외 조건 | (조건 요약)에 해당하지 않는다면 신청 가능해요 |
| 미확인 2개 이상 | 가장 위의 하나만 문장으로, 뒤에 "(확인할 조건 n개 더)" |

**고정 형식에 값만 넣는다. AI가 자유롭게 쓰지 않는다.** `check` 상태일 때만 채운다.

### 추가 항목 조건절 문구 표

"(항목)이 (값)이라면"을 기계적으로 만들면 말이 되지 않는다. `other_benefit`은 값 문구가 "없음"이라 "다른 지원 수혜가 없음이라면"이 된다. 그래서 조합마다 읽히는 조건절을 표에 적어 두고 거기서 고른다. 표는 `values.py`의 `EXTRA_CONDITION_CLAUSES`다.

| 항목 | 예 |
| --- | --- |
| `housing_type` | 월세로 살고 있다면 / 부모님 집에 살고 있다면 |
| `residence_period` | 서울에 산 지 6개월이 안 됐다면 / 1년이 넘었다면 |
| `remaining_semesters` | 졸업까지 1학기 남았다면 |
| `job_seeking_period` | 구직 활동을 시작한 지 6개월이 넘었다면 |
| `employment_insurance` | 고용보험에 가입한 적이 없다면 |
| `other_benefit` | 다른 청년 지원금을 받고 있지 않다면 |
| `household_size` | 혼자 살고 있다면 / 가구원이 4인 이상이라면 |
| `last_gpa` | 직전 학기 성적이 공고 기준 이상이라면 |

표에서 고르는 것이므로 고정 형식 원칙은 그대로다. AI가 문장을 쓰지 않는다.

표에 없는 조합은 조사를 맞춘 기본 형태("(항목)이 (값)이라면")로 만든다. 어색할 수 있지만 문구가 빠져도 문장이 나오는 쪽이 낫다. 조건부 문장이 비면 카드에 상태 문구만 남는다.

### 문장을 만들지 않는 경우

값을 채울 수 없으면 비운다. **지어내지 않는다.**

- 소득 상한(`income_max_pct`)을 모를 때
- 추가 항목의 필요한 값을 모를 때
- 조건 요약이 비었을 때 (인용 검증에 실패한 조건)
- 정책이 "모름"을 필요한 값으로 요구할 때 (데이터 오류다. "성적이 모름이라면"은 말이 되지 않는다)

맨 위 조건으로 문장을 만들 수 없으면 **다음 미확인 조건으로 넘어간다.** 그 조건 때문에 포기하면 카드에 상태 문구만 남는다.

조건부 문장과 미확인 판정은 짝이다. 하나만 있으면 제품이 무용해진다. 소득을 모르는 사용자에게 카드 전부가 "확인이 필요해요"로만 보이면 아무 정보를 주지 못한다. 조건부 문장이 그 빈칸을 메운다(FR08).

## 8. 체크리스트 추출

공고 원문에서 필요 서류와 신청 단계를 뽑는다.

| 항목 | 규칙 |
| --- | --- |
| 서류 | 공고에 있는 것만. 줄마다 하나. 발급처가 공고에 있으면 괄호로 |
| 신청 단계 | 공고에 있는 순서대로. **원문에 없는 단계를 추가하지 않는다** |
| 마지막 항목 | 공식 신청 페이지 이동은 프론트가 붙인다 |

"온라인 신청" 같은 당연해 보이는 단계도 공고에 없으면 넣지 않는다. 절차를 지어내면 사용자가 그 순서대로 준비하다 막힌다.

## 9. 실패 처리

| 경우 | 처리 |
| --- | --- |
| 결과 형식이 깨짐 | 한 번 다시 시도. 또 실패하면 예외 조건 전체 `unknown` |
| 8초 초과 | 예외 조건 전체 `unknown`. **재시도하지 않는다** |
| 속도 제한이나 과부하 | 재시도하지 않는다. 전체 `unknown` |
| `exceptions_text`가 비어 있음 | 판정 생략 |

시간 초과에 재시도를 붙이지 않는 이유는 전체 20초 상한이다. 8초를 다시 쓰면 답변 작성 시간이 없어진다(`../../docs/research/04-llm-api-operations.md` 3절).

어느 경우든 규칙 엔진 결과로 카드는 이미 화면에 있다. **이 역할이 전부 실패해도 제품은 서 있다.** 그 대신 각주가 줄어들고 판정이 미확인으로 남는다.

## 10. 판정 평가 케이스

**실제 수집한 정책의 예외 문장으로 채운다.** 아래는 유형 예시다.

| 번호 | 예외 문장 유형 | 프로필 | 기대 결과 |
| --- | --- | --- | --- |
| J1 | 휴학생 제외 | 휴학 | `unmet` |
| J2 | 휴학생 제외 | 재학 | `met` |
| J3 | 타 지원금 수혜자 제외 | 정보 없음 | `unknown`, 다른 지원 |
| J4 | 타 지원금 수혜자 제외 | 다른 지원 없음 | `met` |
| J5 | 최근 n년 내 동일 사업 참여자 제외 | 정보 없음 | `unknown`, 공고 확인 필요 |
| J6 | 학점 기준 이상 | 성적 모름 | `unknown`, 직전 학기 성적 |
| J7 | "기타 부적격자" 같은 모호 문장 | 아무 프로필 | `unknown` |
| J8 | 서울 소재 대학 재학생 | 서울 거주, 학교 소재 모름 | `unknown`, 공고 확인 필요 |

J7과 J8이 가장 중요하다. 모호한 문장과 정보가 반쯤 있는 상황에서 단정하지 않는지를 본다.
프롬프트를 고칠 때마다 다시 돌린다. 한 번 통과했다고 넘기지 않는다. 낮은 온도를 써도 완전한 재현성은 보장되지 않는다.

## 11. 근거 없는 조건 점검표

정책별로 원문에 있는 조건 목록을 미리 적어 둔다. 본선 당일 화면에 나온 조건이 그 목록에 없으면 1건으로 센다.

| 항목 | 값 |
| --- | --- |
| 목표 | 0건 |
| 점검 범위 | 대표 프로필 5개 × 예외 흐름 3개 |
| 점검 시각 | 13:00~14:30 |

이 점검은 인용 검증기가 잡지 못하는 것을 잡는다. 검증기는 발췌가 원문에 있는지만 본다. 발췌는 맞는데 조건 요약이 원문에 없는 내용을 말하는 경우가 남는다. 조건 요약은 20자로 줄인 문장이라 원문과 문자열이 일치하지 않아서, 문자열 대조로는 잡을 수 없다.

### 자동으로 잡는 것과 사람이 잡는 것

숫자는 기계가 정확하다. 뜻은 사람이 봐야 한다.

| 무엇 | 누가 | 도구 |
| --- | --- | --- |
| 조건 요약의 숫자가 원문에 없음 (`ungrounded_number`) | 자동 | `grounding.py` |
| 근거 없이 조건 요약만 화면에 나감 (`name_without_excerpt`) | 자동 | `grounding.py` |
| **뜻이 어긋난 요약** (원문 "휴학생 제외" → 화면 "재학생만 신청 가능") | 사람 | `grounding-checklist.md` |
| 원문에 아예 없는 조건 | 사람 | `grounding-checklist.md` |

```python
from ai.judgment.grounding import check_conditions

report = check_conditions(result["conditions"], policy["raw_text"])
print(report.summary())   # 지표 슬라이드에 그대로 옮긴다
```

자동 검출로 먼저 걸러내 사람이 볼 목록을 줄인다. 한 자리 수는 건너뛴다 — 요약을 다듬다 생기는 잡음이고, 잡음이 많으면 아무도 점검표를 보지 않는다. 위험한 숫자(금액·비율·나이·기간)는 거의 두 자리 이상이다.

정책별 "원문에 있는 조건 목록"은 정책 데이터가 들어온 뒤 사전 작성한다. 지금은 빈 양식이다.

## 12. 지표 정리 (14:30~15:00)

| 지표 | 출처 | 목표 |
| --- | --- | --- |
| 근거 없는 조건 건수 | 점검표 (11장) | 0건 |
| 인용 검증 통과율과 제거 건수 | 백엔드B 기록 | 통과율 100% |
| 판정 평가 J1~J8 결과 | 평가 표 (10장) | 7개 이상, 미충족 오판 0건 |
| 추천 정확도 | 백엔드A 채점 | 80% 이상 |
| 응답 시간 | 백엔드B 기록 | 첫 카드 2초, AI 설명 15초 |

발표 슬라이드 한 장으로 정리한다. **한계도 같은 장에 적는다.**

수치가 세 군데에 흩어져 있어서(`scoring.Report`, `judge.JudgeStats`, 인용 검증 기록) 모으는 도구를 뒀다. 코드를 못 돌리는 상황을 대비해 같은 구조의 빈 틀이 `metrics-slide.md` 에 있다.

```python
from ai.judgment.metrics import collect

report = collect(
    judgment_report=scoring_report,   # AI B
    judge_stats=judge.stats,          # AI B
    verified_excerpts=42,             # 백엔드B
    removed_excerpts=0,               # 백엔드B
    ungrounded_conditions=0,          # AI B, 점검표에서 센 값
    recommendation_accuracy=0.85,     # 백엔드A
    first_card_seconds=1.2,           # 백엔드B
    answer_seconds=12.4,              # 백엔드B
)
print(report.to_slide())
```

**측정하지 않은 것은 "미측정"이다.** 0이나 100%로 채우지 않는다. 목표가 0건인 지표(근거 없는 조건)와 100%인 지표(인용 검증)는 채우지 않아도 달성처럼 보이는 모양이라 특히 위험하다. 달성(`met=False`)과 미측정(`met=None`)을 다른 상태로 다룬다.

평가 케이스가 아직 실제 공고 문장이 아니거나 용량 부족이 있었으면 경고가 자동으로 붙는다. 그 상태의 수치는 발표에 쓰지 않는다.

| 한계 | 내용 |
| --- | --- |
| 커버리지 | 검수된 20~30건뿐. 전국 실시간 수집이 아니다 |
| 판정의 성격 | 최종 자격 판정이 아니다. 신청 가능성과 근거를 보여줄 뿐이다 |
| 설문 | 29명 편의표집. 비율을 시장 전체로 일반화하지 않는다 |
| 데이터 갱신 | 수동. 확인일로부터 14일이 지나면 재확인 필요로 표시하는 것이 현재 대책이다 |
| 접근성 | 기준을 지켰지만 보조기술 수동 테스트와 전문가 검토는 하지 못했다 |

한계를 먼저 말하는 쪽이 질의응답에서 유리하다. 심사위원이 먼저 지적하면 방어가 되고, 우리가 먼저 말하면 판단으로 보인다.

### 쓰는 방법

운영 경로는 `judge_and_verify()` 다. 판정과 인용 검증을 한 번에 끝내므로 원문에 없는 발췌가 화면으로 나갈 수 없다.

```python
from ai.judgment import ExceptionJudge

judge = ExceptionJudge()
result = judge.judge_and_verify(policy, profile)
# result["conditions"]  검증 통과한 조건. 발췌는 원문에서 되찾은 구간
# result["removed"]     제거된 발췌 기록 (지표용)

results = judge.judge_policies(candidate_policies, profile)  # 동시 실행, 상한 3
```

평가는 `judge_policy` 를 하네스에 넘긴다. 프롬프트를 고칠 때마다 다시 돌린다.

```python
from ai.judgment.scoring import evaluate
report = evaluate(ExceptionJudge().judge_policy)
print(report.summary())
```

### 모델 설정

**모델 이름을 코드에 박지 않는다.** 환경 변수로 넣는다 (`client.py` 상단 표 참고).

| 변수 | 기본값 | 비고 |
| --- | --- | --- |
| `CLAUDE_API_KEY` | 없음 (필수) | 각자 로컬 환경 변수에만. 커밋·채팅 공유 금지 |
| `CLAUDE_MODEL` | 자리표시 | 캠프에서 받는 이름을 넣는다. 코드를 고치지 않는다 |
| `CLAUDE_MAX_TOKENS` | 1024 | |
| `CLAUDE_TEMPERATURE` | 0.0 | 판정이므로 낮게 |

의존성은 `anthropic` 하나다. **버전 고정은 백엔드B가 의존성 목록에서 한다.** `client.py` 는 지연 import 하므로 패키지가 없어도 이 폴더의 테스트는 전부 돌아간다.
