## 1. 목표

사용자가 편하게 말해도 프로필과 의도를 정확히 읽고, 판정이 갈리는 것만 묻고, 결론 먼저·근거는 각주로 답하는 대화.

여기서 실패하면 제품이 그냥 검색 필터가 된다. 대화형이 기존 서비스와의 유일한 차별점이므로, 데모에서 관객이 "오" 하는 순간은 5번(후속 질문으로 카드가 바뀜)과 6번(한마디로 프로필이 바뀜)에서 나온다.

## 2. 담당 범위

메시지 해석, 후속 질문 선택과 문장, 답변 작성, 각주 매핑, 관련 질문 칩, 대화 평가.

| AI가 하는 것 | 코드가 하는 것 |
| --- | --- |
| 자연어에서 관심 분야·생활 사건·프로필 변경 추출 | 어떤 정보를 물을지 **선택** |
| 답변 설명 작성 | 판정 상태 확정 |
| (P1) 질문 문장을 맥락에 맞게 다듬기 | D-day와 날짜 계산 |
| — | 각주 번호 부여 |
| — | 이미 물었거나 건너뛴 항목 기록 |

경계가 이렇게 그어진 이유는 하나다. **모델이 잘하는 일(문장 이해와 생성)과 못 믿을 일(셈, 날짜, 일관된 판정)을 섞지 않는다.**

## 3. 메시지 해석

### 뽑아낼 것

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 의도 | `find_policy`, `policy_question`, `compare`, `result_only`, `out_of_scope`, `smalltalk` | 하나만 |
| 프로필 변경 | 항목 이름, 값, 시점(`current` 또는 `planned`) | 여러 개 가능 |
| 추가 항목 답변 | 항목 이름과 값 | 묻지 않았어도 말했으면 반영 |
| 관심 분야 | 추가할 분야, 제외할 분야 | |
| 언급된 정책 | 정책 번호 | 특정 정책 질문일 때 |

항목 이름과 허용 값은 `../../docs/01-glossary-profile.md` 2~3장이 유일한 기준이다. **표에 없는 항목을 만들지 않는다.**

### 해석 기준

- 확실히 말한 것만 반영한다. 추측해서 채우지 않는다.
- 미래 계획("다음 학기에 휴학해요")은 시점을 `planned`로 두고 **프로필을 바꾸지 않는다.** 대신 "휴학 후 기준으로 볼까요, 지금 기준으로 볼까요?"를 후속 질문으로 붙인다. 이건 `status` 의 예시이고, **항목별 문구는 5장 표**를 쓴다.
- 폼 값과 다르게 말하면 **대화 값**을 따른다.
- 숫자 소득("월 200 벌어요")은 구간으로 바꾸지 않는다. 개인 소득과 가구 소득 기준이 다르므로 "가구 소득 구간을 알려주시면 더 정확해요"로 연결한다.
- **거주지(`region`)는 대화로 바꾸지 않는다.** "서울 밖으로 이사했어요" 같은 발화도 읽기는 하되 프로필에 반영하지 않고 버리고, 버린 이유를 `region_is_fixed` 로 기록한다. `../../docs/01-glossary-profile.md` 2장이 `region` 을 입력받지 않는 `seoul` 고정 항목으로 정했고, 서버 프로필 모델도 `seoul` 한 값만 받으며 변경 가능한 항목 목록에 `region` 이 없다. 반영하면 프로필이 서버 검증에서 막힌다. 시점이 `planned` 여도 같다. 버리는 시점이 값 검증보다 앞이라 보류 목록에도 들어가지 않는다.

`region` 을 "모르는 항목"으로 묶지 않고 따로 기록하는 이유는, 모델이 표에 없는 이름을 보낸 것(`unknown_field`)과 사용자가 제도상 바꿀 수 없는 항목을 말한 것을 지표에서 구분해야 하기 때문이다. 한 코드로 합치면 모델 품질 문제인지 발화 유형인지 알 수 없다. 거주지 값 자체는 서버가 프로필에 담아 보내므로 읽기·표시·정렬에는 그대로 쓴다. 지워지는 것은 변경 경로뿐이다.

미래 계획을 바로 반영하지 않는 이유는, 지금 신청할 수 있는 제도를 찾는 것이 목적이기 때문이다. 휴학 예정자에게 휴학생 전용 제도를 지금 신청 가능한 것처럼 보여주면 틀린 안내가 된다.

### 의도별 동작

| 의도 | 동작 |
| --- | --- |
| `find_policy` | 전체 흐름 |
| `policy_question` | 그 정책 판정 위주로 답변, 카드 하나 강조 |
| `compare` (P1) | 두 정책의 조건·혜택·마감 비교 문단 |
| `result_only` | 후속 질문 생략, 현재 결과 정리 |
| `out_of_scope` | "행정 절차나 법률 상담은 아직 도와드리기 어려워요" 한 줄 + 할 수 있는 것 안내 |
| `smalltalk` | 한 줄 응대 후 정책 찾기 유도 |

범위 밖과 잡담은 규칙 재계산과 판정을 건너뛰고 바로 종료한다. 시간 예산을 쓰지 않는다.

## 4. 후속 질문 선택

규칙 엔진이 준 미확인 항목 목록에서 고른다. 순서대로 적용한다.

1. 미확인 항목 목록을 모은다. **이미 물었거나 건너뛴 항목은 뺀다.**
2. 항목마다, 답에 따라 상태가 바뀔 수 있는 표시 중 정책 수를 센다.
3. 수가 가장 많은 항목을 고른다.
4. 같으면 더 위에 있는 정책에 영향을 주는 항목.
5. 그래도 같으면 프로필 항목 표의 순서.
6. 고를 항목이 없으면 **묻지 않는다.**

한 턴에 하나만 묻는다. `result_only` 의도를 보이면 그 세션에서는 먼저 묻지 않는다.
**선택은 코드가 하고 AI는 문장만 다듬는다.** 선택을 모델에게 맡기면 같은 상황에서 다른 질문이 나와 데모가 흔들린다.

건너뛴 항목을 다시 묻지 않는 것은 세션이 기록한다(`../../docs/03-api-contract.md` 11장). 이걸 놓치면 사용자가 "모르겠어요"라고 답한 질문을 또 받게 되고, 대화형이라는 인상이 한순간에 깨진다.

## 5. 후속 질문 문구

화면 문구로 고정한다. 이유 문구의 ○○와 n은 실제 영향받는 정책명과 수로 채운다.
**문장 자체를 AI가 새로 만들지 않는다.** P1에서만 맥락에 맞게 다듬기를 허용한다.

| 항목 | 질문 | 이유 문구 | 선택지 |
| --- | --- | --- | --- |
| `income_bracket` | 가구 소득이 어느 정도인지 아세요? | ○○ 등 n개 제도가 소득 기준으로 갈려요 | 소득 구간 5개 |
| `district` | 어느 구에 사세요? | 구에서 하는 지원이 있어요 | 자주 쓰는 구 5개 + 직접 입력 |
| `housing_type` | 지금 어떻게 지내고 계세요? | 월세 지원은 주거 형태에 따라 달라요 | 부모님 집, 월세, 전세, 기숙사, 기타 |
| `residence_period` | 서울에 산 지 얼마나 되셨어요? | 거주 기간 조건이 있는 제도가 있어요 | 6개월 미만, 6개월~1년, 1년 이상 |
| `remaining_semesters` | 졸업까지 몇 학기 남았어요? | 졸업예정자 대상 제도가 있어요 | 1학기, 2학기 이상 |
| `job_seeking_period` | 구직 활동한 지 얼마나 됐어요? | 구직 기간 조건이 있어요 | 6개월 미만, 6개월 이상 |
| `employment_insurance` | 일하면서 고용보험에 가입한 적 있어요? | 훈련 지원 조건과 관련 있어요 | 있음, 없음, 모르겠어요 |
| `other_benefit` | 지금 받고 있는 다른 청년 지원금이 있나요? | 중복으로 못 받는 제도가 있어요 | 있음, 없음 |
| `household_size` | 함께 사는 가족은 몇 명이에요? | 소득 기준이 가구원 수로 달라져요 | 1인, 2인, 3인, 4인 이상 |
| `last_gpa` | 직전 학기 성적이 공고 기준 이상인가요? | 성적 조건이 있는 장학금이 있어요 | 기준 이상, 기준 미만, 모르겠어요 |

`housing_type` 에 "기타"를 둔 이유는 허용 값 5개(`../../docs/01-glossary-profile.md` 3장)를 선택지가 전부 덮어야 하기 때문이다. 없으면 고시원·하숙에 사는 사용자는 답할 경로가 아예 없다.

모든 질문에 **건너뛰기**를 붙인다. 이유 문구를 붙이는 목적은 심문처럼 느껴지지 않게 하는 것이다. 왜 묻는지 알면 사용자가 답할 이유가 생긴다.

### 직접 입력은 `district` 한 항목만

**직접 입력은 `district` 에서만 연다.** 나머지 항목은 닫고, 대신 **선택지가 허용 값을 전부 덮게 한다.** 이 둘은 짝이다.

후속 질문 답변은 해석 단계를 건너뛰고 값을 그대로 프로필에 넣는다(`../../docs/03-api-contract.md` 3장). 그래서 허용 값이 코드 값(`monthly_rent`, `4_plus`)인 항목에 직접 입력을 열면, 사용자가 무엇을 적어도 허용 값 밖이라 규칙 엔진이 모르는 값이 프로필에 들어간다. 답을 받은 것처럼 보이지만 판정은 그대로 미확인이라 **건너뛰기보다 나쁘다.**

`district` 는 허용 값이 자치구 이름 25개라 사용자가 타이핑한 글자가 그대로 허용 값이 된다. 버튼은 자주 쓰는 5개뿐이므로(25개를 깔면 질문 카드가 화면을 덮는다) 직접 입력이 나머지 20개를 답할 유일한 경로다.

### 개수를 모를 때의 이유 문구

| 항목 | 개수를 모를 때 쓰는 이유 문구 |
| --- | --- |
| `income_bracket` | 소득 기준으로 판정이 갈리는 제도가 있어요 |
| 그 밖의 항목 | 위 표의 이유 문구를 그대로 쓴다 |

`/session` 의 첫 후속 질문은 정책 정보 없이 만들어져 개수를 모른다. 그때 위 표의 문장을 그대로 쓰면 "0개 제도가 소득 기준으로 갈려요"가 화면에 나간다. 개수 자리(n)를 가진 항목은 **`income_bracket` 하나뿐**이고, 나머지 항목은 이유 문구에 개수가 없어 위 표의 문장이 그대로 성립한다.

개수를 모른다고 이유 자체를 지우지는 않는다. 이유가 없으면 질문이 심문이 된다. 개수 자리를 새로 만드는 항목은 이 표에 개수 없는 형태를 함께 적는다. 빠뜨리면 "이 답변으로 판정이 갈리는 제도가 있어요"가 대신 나가고, 화면 문구가 표 밖에서 정해진다.

### planned 확인 질문 문구

미래 계획(3장)에 붙이는 확인 질문이다. planned 변경은 `status` 만이 아니라 `housing_type`, `income_bracket`, `household_size` 등 어느 항목에서도 온다. ○○는 바뀔 값의 화면 문구로 채운다.

| 바뀔 항목 | 질문 | 이유 문구 |
| --- | --- | --- |
| `age` | ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 나이가 바뀌면 맞는 제도가 달라져요 |
| `district` | ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 사는 곳이 바뀌면 맞는 제도가 달라져요 |
| `status` | ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 신분이 바뀌면 맞는 제도가 달라져요 |
| `income_bracket` | 가구 소득 ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 가구 소득이 바뀌면 판정이 달라져요 |
| `housing_type` | ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 주거 형태가 바뀌면 맞는 제도가 달라져요 |
| `residence_period` | 서울 거주 기간 ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 서울 거주 기간이 바뀌면 판정이 달라져요 |
| `remaining_semesters` | 남은 학기 ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 남은 학기가 바뀌면 맞는 제도가 달라져요 |
| `job_seeking_period` | 구직 기간 ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 구직 기간이 바뀌면 판정이 달라져요 |
| `employment_insurance` | 고용보험 가입 이력이 바뀐 뒤 기준으로 볼까요, 지금 기준으로 볼까요? | 고용보험 가입 이력이 바뀌면 판정이 달라져요 |
| `other_benefit` | 다른 지원 수혜 여부가 바뀐 뒤 기준으로 볼까요, 지금 기준으로 볼까요? | 중복으로 못 받는 제도가 있어요 |
| `household_size` | 가구원 수 ○○ 기준으로 볼까요, 지금 기준으로 볼까요? | 가구원 수가 바뀌면 소득 기준이 달라져요 |
| `last_gpa` | 직전 학기 성적이 바뀐 뒤 기준으로 볼까요, 지금 기준으로 볼까요? | 직전 학기 성적이 바뀌면 판정이 달라져요 |
| 라벨을 못 구했거나 표에 없는 항목 | 바뀐 뒤 기준으로 볼까요, 지금 기준으로 볼까요? | 조건이 바뀌면 판정이 달라져요 |

`region` 행은 없다. `../../docs/01-glossary-profile.md` 2장이 거주지를 `seoul` 고정으로 정했으므로 "거주지가 바뀐 뒤 기준"이라는 시점 자체가 존재할 수 없고, `region` 변경은 시점과 무관하게 버려져 보류 목록에 들어가지 않는다(3장).

선택지는 두 개다. **바뀐 뒤 기준으로**(`planned`), **지금 기준으로**(`current`). 직접 입력은 열지 않는다. 기준 시점은 둘 중 하나이고, 시점으로 읽을 수 없는 글자가 들어오면 쓸 수 없다.

항목마다 틀을 따로 두는 이유는, 라벨만 끼우면 문장이 되는 항목("휴학 기준으로 볼까요")과 항목 이름이 앞에 있어야 뜻이 통하는 항목("가구원 수 3인 기준으로 볼까요")이 섞여 있기 때문이다. 하나의 틀로 밀면 "있음 기준으로 볼까요"(고용보험)처럼 무슨 말인지 모르는 문장이 나온다. 라벨을 못 구하면 빈 자리를 내보내지 않고 라벨 없는 기본 문구를 쓴다. 선택지 문구가 같은 말이라 무엇을 고르는지는 알 수 있다.

이 질문의 항목 이름은 **프로필 항목이 아니라 `planned_basis`** 다. 묻는 것이 "휴학 예정을 반영할까"가 아니라 "어느 시점을 기준으로 판정할까"이기 때문이다. 이름을 `status` 로 두면, 후속 질문 답변은 해석을 건너뛰고 값을 그대로 프로필에 넣으므로(`../../docs/03-api-contract.md` 3장) `status="planned"` 라는 허용 값 밖 값이 프로필에 박힌다. 답변은 프로필에 들어가지 않고 다음 해석의 기준 시점으로 세션이 들고 있는다(`../../docs/03-api-contract.md` 11장).

**건너뛰면 지금 기준을 유지한다.** planned 변경은 애초에 프로필에 반영하지 않았으므로(3장) 아무것도 하지 않는 것이 곧 지금 기준이다.

## 6. 답변 구성

| 순서 | 내용 | 기준 |
| --- | --- | --- |
| 1 | 요약 | 한 문장. "신청 가능성이 높은 제도 n개, 확인이 필요한 제도 n개를 찾았어요." |
| 2 | 정책별 설명 | 표시 순서대로 최대 5개, 정책당 1~2문장. 왜 맞는지 또는 무엇이 남았는지 |
| 3 | 조건 안내 | `check`가 있으면 남은 조건을 한 문장으로 묶어 |
| 4 | 마감 강조 | 마감 임박이 있으면 한 문장 |
| 5 | 고정 문구 | "최종 신청 전 공식 공고에서 다시 확인하세요" |

### 말투와 길이

해요체. 과장·감탄·이모지 없음. 요약부터 고정 문구까지 합쳐 **600자 이내.** 정책명은 데이터의 제목 그대로.

600자로 묶는 이유는 카드가 이미 정보를 담고 있기 때문이다. 답변이 길면 카드를 읽지 않고, 그러면 각주와 조건 판정표라는 우리 차별점이 묻힌다.

### 근거 규칙

- 판정·조건·금액·날짜가 든 문장에는 **반드시 각주**를 붙인다. 각주 없는 판정 문장은 출력하지 않는다.
- 각주는 규칙 엔진과 AI B가 넘긴 조건 결과의 발췌에만 연결한다. **새 발췌를 만들지 않는다.**
- 각주 번호는 서버가 부여한 값을 쓴다. 직접 번호를 매기지 않는다.
- 금액과 날짜는 데이터 필드 값만 쓴다.
- 판정 상태는 이미 확정된 값을 설명만 한다. **답변에서 상태를 새로 판단하지 않는다.**

### 형식

답변은 스키마를 강제하지 않는다. 형식 제약이 문장 품질을 떨어뜨린다는 근거가 있고, 각주 번호는 이미 코드가 부여한 값을 쓰기 때문에 강제할 이유가 없다(`../../docs/research/04-llm-api-operations.md` 1절).

### 금지 표현

대상입니다, 받을 수 있어요, 확실히, 무조건, 100%, 보장, 걱정 마세요

### 결과 없음일 때

"지금 조건으로는 맞는 제도를 찾지 못했어요." + 조건을 넓히는 방법 + 우리 데이터 범위 한 줄.

## 7. 관련 질문 칩 (P1)

| 상황 | 칩 예 |
| --- | --- |
| `check`가 있음 | 소득 기준 확인하는 방법 알려줘 |
| `unlikely`가 있음 | 조건이 안 맞는 이유가 뭐야? |
| 카드 2개 이상 | 상위 두 개 비교해줘 |
| 마감 임박 있음 | 마감 임박한 것부터 준비 순서 알려줘 |

최대 3개. 이미 물어본 것과 같은 칩은 뺀다. 일정이 밀리면 고정 문구 3개로 대체한다(`../../docs/00-overview.md` 빼는 순서 2번).

## 8. 해석 테스트 케이스

사전 준비 산출물이다. 프롬프트를 고칠 때마다 다시 돌린다.

| 입력 | 기대 해석 |
| --- | --- |
| 방학 동안 취업 준비하면서 생활비 지원 받을 수 있는 거 있어? | `find_policy`, 관심 분야 취업·생활비 |
| 저 이번 달부터 자취해요 월세로 | 주거 형태 월세, 관심 분야 주거 추가 |
| 다음 학기에 휴학할 거예요 | 상태 휴학 `planned`, 프로필 유지, 확인 질문 |
| 사실 저 졸업했어요 | 상태 졸업 후 구직으로 변경 |
| 두 번째 거랑 세 번째 거 비교해줘 | `compare`, 표시 순서로 정책 특정 |
| 그냥 결과만 보여줘 | `result_only` |
| 전입신고 어떻게 해? | `out_of_scope` |
| 부모님이랑 같이 살아요 | 주거 형태 부모님 집 |
| 월 150 벌어요 | 프로필 변경 없음, 가구 소득 안내 |
| 고마워! | `smalltalk` |

## 9. 대화 평가 케이스

| 번호 | 대화 | 통과 기준 |
| --- | --- | --- |
| C1 | P1 프로필 + 데모 첫 문장 | 요약 문장 있음, 각주 있음, 600자 이내, 금지 표현 없음 |
| C2 | C1 후 소득 질문에 "모르겠어요" | 같은 질문 다시 안 함, 다음 항목으로 |
| C3 | 저 이번 달부터 자취해요 | 프로필 변경 표시, 주거 정책 등장 |
| C4 | 다음 학기에 휴학할 거예요 | 프로필 유지, 확인 질문 |
| C5 | 결과만 보여줘 | 후속 질문 없음 |
| C6 | 전입신고 어떻게 해? | 범위 밖 안내 한 줄 |
| C7 | 결과 없는 관심 분야 | 결과 없음 안내와 넓히는 방법 |
| C8 | 모든 항목 건너뛰기 | 질문 멈춤, `check` 결과 정리 |

C2와 C8이 가장 중요하다. 이 두 개가 깨지면 후속 질문이 심문이 된다.
