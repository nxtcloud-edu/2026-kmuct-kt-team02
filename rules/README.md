# 규칙 엔진 (담당: 백엔드A)

> 출처: 역할별 설계서 3-4~3-8. 본선 당일 오전(09:00~10:30)에 `docs/02-requirements-ears.md` + `docs/01-glossary-profile.md` + 이 파일을 KIRO Spec 요구사항 입력으로 넣는다.
> **AI 없이도 정확한 결과를 내는 것이 이 모듈의 존재 이유다.** AI가 전부 실패하거나 늦어도 이 모듈의 출력만으로 카드가 화면에 보여야 한다.

## 1. 목표

AI 없이도 정확한 1차 결과를 **1초 안에** 내는 규칙 엔진이다. 프로필과 정책 데이터만 가지고 후보를 고르고, 조건을 판정하고, 순서를 정해서 넘긴다. AI 판정이 늦거나 실패해도 사용자는 이 결과로 만들어진 카드를 이미 보고 있다. 그래서 이 모듈은 느려질 여지도, 애매하게 답할 여지도 없다. 같은 입력이면 항상 같은 출력이 나와야 한다.

## 2. 담당 범위

| 구분 | 항목 |
| --- | --- |
| 한다 | 규칙 조건 판정 (나이·지역·신분·소득·추가 항목) |
| 한다 | D-day 계산과 마감 배지 결정 |
| 한다 | 데이터 상태 판정 (`verified`, `recheck`, `closed`, `upcoming`) |
| 한다 | 후보 선정 |
| 한다 | 정렬 |
| 한다 | 미확인 항목 목록 산출 |
| 하지 않는다 | 문장형 예외 조건 판정 → AI B |
| 하지 않는다 | 답변 문장 작성 → AI A |
| 하지 않는다 | 후속 질문 문구 작성 → AI A |

하지 않는 것의 경계는 명확하다. 규칙 엔진은 표로 표현된 조건만 다룬다. `exceptions_text`처럼 문장으로만 남은 조건은 건드리지 않고 AI B에 넘긴다. 어떤 후속 질문을 할지 고를 재료(미확인 항목 목록)는 내보내지만, 질문 문장 자체는 만들지 않는다.

## 3. 입력과 출력

### 입력

| 입력 | 내용 | 참고 |
| --- | --- | --- |
| 프로필 | 기본 5항목 + 추가 항목 | [`../docs/01-glossary-profile.md`](../docs/01-glossary-profile.md) 2~3장 |
| 정책 데이터 | 수집·검수 완료된 정책 전체 | [`../docs/04-data-schema.md`](../docs/04-data-schema.md) 1장 |
| 오늘 날짜 | 한국 시간 기준 오늘 | 날짜 계산의 유일한 기준점 |

### 출력

| 출력 | 내용 | 쓰는 곳 |
| --- | --- | --- |
| 후보 목록 | 정렬이 끝난 순서 그대로 | 카드 표시 순서 |
| 정책별 규칙 조건 결과 | 조건 이름, `met`/`unmet`/`unknown`, 판정 주체 `rule`, 근거 발췌 연결 | 조건 판정표 |
| 마감 정보 | 접수 시작일, 마감일, D-day, 배지 문구, 마감 임박 여부 | 카드 배지 |
| 미확인 항목 목록 | 정책마다 남은 미확인 프로필 항목 | AI A의 후속 질문 선택 |
| 기본 표시 5개 | `likely`와 `check` 중 상위 5개 | 첫 화면 |
| 접힌 `unlikely` 개수 | 접힌 영역에 들어갈 개수 | 접힌 영역 표시 |

받는 쪽은 백엔드B다. 백엔드B가 AI B의 예외 조건 결과와 합쳐 최종 판정 상태를 확정하고 응답으로 내보낸다. 각 출력 항목이 응답의 어느 필드로 가는지는 [`../docs/03-api-contract.md`](../docs/03-api-contract.md) 4장을 따른다. 넘기는 형식은 **10:30 확정, 13:00 동작**이 기준이다.

## 4. 조건 판정

| 조건 | 충족 (`met`) | 미충족 (`unmet`) | 미확인 (`unknown`) |
| --- | --- | --- | --- |
| 나이 | `age_min` 이상 `age_max` 이하 | 범위 밖 | 경계 나이(`age_min` 또는 `age_max`와 같음)이고 공고에 기준일이 따로 있을 때 |
| 지역 | `regions`에 서울 또는 전국 포함. 자치구 정책은 자치구 일치 | 서울 외 거주인데 서울 정책, 또는 다른 자치구 | 자치구 정책인데 자치구 미선택 |
| 신분 | `statuses`에 현재 상태 포함 | 미포함 | 없음 |
| 소득 | 사용자 구간 상한 ≤ 기준 | 사용자 구간 하한 ≥ 기준 | 구간이 기준에 걸침, 또는 `unknown` |
| 추가 항목 | 답변이 필요한 값과 같음 | 다름 | 아직 묻지 않았거나 건너뜀 |

`income_max_pct`가 비어 있으면 소득 조건을 판정표에 **표시하지 않는다**. 조건이 없는 정책에 "소득: 미확인"을 붙이면 아무 근거 없이 `check`로 떨어지고, 소득을 모르는 사용자에게 `likely`를 보여주자는 데이터 설계 의도와 정면으로 어긋난다.

소득 비교는 구간 대 상한 비교다. 예를 들어 기준이 150%이고 사용자가 `100_150`이면 구간 상한 150이 기준과 같으니 충족이다. 기준이 120%이고 사용자가 `100_150`이면 구간이 기준선을 걸치므로 미확인이다. 구간 값의 하한·상한 숫자는 [`../docs/01-glossary-profile.md`](../docs/01-glossary-profile.md) 2장 소득 구간 의미 표를 그대로 쓴다.

각 규칙 조건에는 정책 데이터의 `condition_sources`에 있는 문장을 발췌로 연결한다. 발췌 없는 조건은 화면에 나갈 수 없으므로, 판정이 되더라도 근거 문장이 비어 있으면 검수 필요로 기록한다.

규칙 조건과 AI 조건이 같은 내용을 다르게 판정하면 **규칙 조건을 따른다**. 판정 상태(`likely`/`check`/`unlikely`)를 정하는 조합 규칙은 [`../docs/01-glossary-profile.md`](../docs/01-glossary-profile.md) 4장을 따르고, 이 문서에서 다시 정하지 않는다.

## 5. 마감과 데이터 상태

| 경우 | 배지 | 기본 결과 노출 | 데이터 상태 |
| --- | --- | --- | --- |
| 마감일이 오늘 | 오늘 마감 | 노출 | `verified` |
| 마감까지 1~7일 | 마감 임박 D-n | 노출 | `verified` |
| 마감까지 8일 이상 | D-n | 노출 | `verified` |
| 마감일 없음 | 상시 접수 | 노출 | `verified` |
| 시작일이 오늘 이후 | 접수 예정 (M.D 시작) | 노출 | `upcoming` |
| 마감일 지남 | 표시 안 함 | **제외** | `closed` |
| 확인일로부터 14일 초과 | 기존 배지 + 재확인 필요 | 노출 | `recheck` |

모든 날짜 계산은 한국 시간 기준이다. **D-day는 코드만 계산한다. AI에게 날짜 계산을 시키지 않는다.** 날짜 산수는 틀리면 바로 눈에 보이고 신뢰를 잃는 부분이라 AI에 맡길 이유가 없다.

재확인 필요는 배지를 덮어쓰지 않고 덧붙이는 표시다. 마감 임박이면서 확인일이 오래된 정책은 두 표시가 같이 붙는다.

## 6. 후보 선정과 표시

1. 후보: 관심 분야가 하나 이상 겹치고(`all` 선택 시 전부 해당), 데이터 상태가 `closed`가 아닌 정책
2. 후보마다 판정 상태를 매긴다
3. 기본 표시: `likely`와 `check` 중 정렬 상위 5개
4. 접힌 영역: `unlikely` 중 정렬 상위 3개
5. `likely`와 `check`가 0개면 결과 없음 흐름으로 넘긴다

출처와 확인일이 둘 다 있지 않은 정책은 후보에서 제외한다(FR12). 규칙 엔진 단계에서 걸러야 뒤 단계에서 근거 없는 카드가 만들어질 여지가 없다.

## 7. 정렬

| 순서 | 기준 |
| --- | --- |
| 1 | 판정 상태: `likely` → `check` → `unlikely` |
| 2 | 마감 7일 이내 먼저 |
| 3 | 마감일 빠른 순. 상시 접수는 뒤, 접수 예정은 그 뒤 |
| 4 | 관심 분야 일치 수 많은 순. 최근 대화에서 언급된 분야 우선 |
| 5 | `id` 순 (동점 처리) |

5번까지 내려오면 순서가 하나로 정해진다. 같은 입력에 같은 순서가 나와야 데모에서 카드 자리가 흔들리지 않는다.

## 8. 미확인 항목 목록

정책마다 미확인으로 남은 조건 중 프로필 항목에 해당하는 것(나이 경계, 자치구, 소득, 추가 항목)을 목록으로 내보낸다. AI A가 이 목록을 보고 어떤 질문을 할지 고른다. 어떤 정책의 판정에 영향을 주는지도 함께 넘겨야 "가장 많은 후보의 판정을 바꾸는 것부터" 고를 수 있다.

항목 이름은 [`../docs/01-glossary-profile.md`](../docs/01-glossary-profile.md) 2~3장의 필드명을 그대로 쓴다. 표에 없는 항목은 만들지 않는다. 규칙 엔진이 표 밖의 항목을 내보내면 대화에서 묻지 않기로 한 것을 묻게 된다.

## 9. 예외 처리

| 상황 | 처리 |
| --- | --- |
| 후보가 0개 | 결과 없음 흐름으로 넘긴다 |
| 프로필 필수 항목 누락 | 입력 오류로 돌려보낸다 |
| 자치구 미선택인데 자치구 정책 | 미확인으로 두고 자치구를 미확인 항목 목록에 넣는다 |
| 정책 데이터에 필수 필드가 비어 있음 | 해당 정책을 후보에서 제외하고 검수 필요로 기록 |
| 추가 항목을 건너뜀 | 미확인으로 유지하고 다시 묻지 않도록 세션에 기록 |

어느 경우에도 규칙 엔진이 멈추거나 빈 응답을 내지 않는다. 데이터 한 건이 잘못돼 있으면 그 한 건만 빠지고 나머지 결과는 정상으로 나가야 한다.

## 9-1. 구현 현황과 백엔드B 연결 방법

구현은 `rules/` 아래 모듈로 끝났다. **외부 의존성 없이 표준 라이브러리만 쓴다.**
Pydantic 과 `server` 를 아는 곳은 `repository.py` 하나뿐이다. 그래서 웹 프레임워크·인증·저장 수단이 바뀌어도 판정 로직은 그대로 남는다.

| 모듈 | 역할 |
| --- | --- |
| `constants.py` | 고정 값 전부. 문자열을 코드에 직접 쓰지 않는다 |
| `loader.py` | 정책 로드와 필드 검증. 한 건이 잘못돼도 그 건만 빠진다 |
| `validate.py` | 프로필 값 2차 검증. 허용 값 밖은 미확인으로 되돌린다 |
| `conditions.py` | 나이·지역·신분·소득·추가 항목 판정 |
| `deadline.py` | D-day, 배지, 데이터 상태 |
| `candidates.py` | 후보 제외, 상태 결정 |
| `sorting.py` | 정렬, 기본 표시 5개와 접힌 3개 분할 |
| `unknowns.py` | 미확인 항목 목록 |
| `saved.py` | 저장 정책 조회 (관심 정책 저장용) |
| `engine.py` | 판정 진입점 |
| `repository.py` | 백엔드B 프로토콜 어댑터 |

### 연결 — 백엔드B 가 할 일 (한 줄)

```python
store, rule_engine = rules.repository.build("data/policies/policies.json")
app = create_app(rule_engine=rule_engine, policy_catalog=store)
```

`PolicyStore` 가 `server/policy_repository.py` 의 `PolicyRepository`(`get`, `count_verified`)를,
`RuleEngineAdapter` 가 `server/rule_engine.py` 의 `RuleEngine`(`evaluate`)과
`server/api/policies.py` 가 부르는 `evaluate_policy` 를 만족한다.

**연결 전 상태를 직접 확인했다.** `create_app()` 기본값으로는
`/health` 가 `policy_dependency=unconnected`, `verified_policy_count=null` 을 돌려주고
`/session` 은 503 "규칙 엔진 의존성이 연결되지 않았습니다" 로 끝난다.

연결하면 다음이 동작한다 (실측).

| 경로 | 결과 |
| --- | --- |
| `GET /health` | `verified_policy_count=5`, `policy_dependency=connected` |
| `POST /session` | 200. 카드 3장(`likely` 2, `check` 1), `profile.region=seoul` |
| `GET /policies/{id}` | 200. 조건별 판정·각주·출처·확인일 포함. 마감·분야 불일치 정책도 열린다 |
| `PATCH /session/{id}/profile` | 200. 추가 항목을 넣으면 `check` → `likely` 로 바뀐다 |

### `RuleEngine` Protocol 에 빠진 선언

`server/api/policies.py` 53행이 `rule_engine.evaluate_policy(profile, policy)` 를 부르는데
`server/rule_engine.py` 의 `RuleEngine` Protocol 에는 그 메서드가 없다.
어댑터에는 구현해 두었으니 동작하지만, **Protocol 에 선언을 추가해야** 다른 구현체나
테스트 더블이 같은 실수를 반복하지 않는다.

```python
class RuleEngine(Protocol):
    def evaluate(self, profile: Profile, *, limit: int = 5) -> RuleEngineResult: ...
    def evaluate_policy(self, profile: Profile, policy: Policy) -> PolicyEvaluation: ...
```

### 계약 차이를 어댑터가 흡수한다

| 문제 | 처리 |
| --- | --- |
| `evaluate(profile, *, limit)` 에 `today` 와 정책 데이터가 없다 | 어댑터가 주입한다. 판정 함수는 `today` 를 인자로 받아야 같은 입력에 같은 출력이 나온다. `clock` 을 바꿔 끼우면 마감 경계 테스트가 날짜와 무관해진다 |
| `RuleEngineResult` 에 `unlikely` 목록 자리가 없다 | 계약대로 개수만 넘기고 목록은 `latest_hidden_unlikely()` 로 꺼낸다. 계약을 임의로 바꾸지 않았다 |
| `footnote_id` 가 1 이상 정수 필수다 | 발췌가 없는 조건에도 번호를 매긴다. 각주를 걸 수 있는지는 `excerpt` 유무로 판단한다 |
| 날짜 형식 | `YYYY-MM-DD` 만 받는다. `date.fromisoformat` 은 `20260920` 도 받지만 프론트는 거부하므로 맞췄다 |

### 미확정

| 항목 | 이유 |
| --- | --- |
| 나이 `unknown` 분기 | "경계 나이 + 공고에 기준일 별도"를 판별할 필드가 데이터에 없다. `AskableProfileField` 에 `age` 가 없어 물을 수도 없다. `met`/`unmet` 2갈래로 구현했다 |
| 정렬 4번 "최근 대화에서 언급된 분야 우선" | 규칙 엔진 입력에 대화 맥락이 없고 `RuleEngine.evaluate` 도 프로필만 받는다. 관심 분야 일치 수까지만 구현했다 |
| 소득 구간 경계 중복 | `under_50`(0~50)과 `50_100`(50~100)이 50에서 겹친다. 정책 상한이 정확히 50일 때 `50_100` 사용자가 미충족이 되는데 실제 소득 50%는 충족이다. 하한을 51·101·151로 두거나 미충족 비교를 `>` 로 바꿔야 한다 |
| 자치구 필수 여부 | `../data/profiles/README.md` 6장 참고. 문서는 선택, 코드는 필수다 |

- [ ] 조건별 근거 문장(`condition_sources`) 열이 스프레드시트에 빠짐없이 채워졌는지 확인

## 11. 완료 기준

- [ ] 규칙 판정이 대표 프로필 P1~P5에서 정답셋과 일치
- [ ] 폼 제출 후 1차 결과가 1초 이내
- [ ] 추천 정확도 80% 이상
- [ ] AI를 일부러 끊어도 카드가 규칙 결과로 표시됨
- [ ] 마감 지난 정책이 기본 결과에 없음
