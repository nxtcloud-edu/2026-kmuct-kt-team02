## 3. 상세 명세

### 3-1. 레이아웃

| 화면 폭 | 배치 |
| --- | --- |
| 데스크톱 1024px 이상 | 왼쪽 대화 영역(최대 폭 720px), 오른쪽 상세 패널(폭 400px, 카드 선택 시 열림) |
| 모바일 1024px 미만 | 대화 영역 전체 폭, 상세는 하단 시트(화면 높이 90%까지) |
| 공통 | 상단에 프로필 요약 바 고정, 하단에 입력창 고정 |

발표 시연은 데스크톱 기준으로 다듬고, 모바일은 깨지지 않는 수준까지만 맞춘다.

### 3-2. 온보딩 화면

| 구성 요소 | 명세 |
| --- | --- |
| 제목 | "지금 받을 수 있는 청년 지원, 30초면 찾아요" |
| 설명 | "기본 정보만 알려주시면 바로 찾아볼게요. 나머지는 대화하면서 여쭤볼게요." |
| 나이 | 숫자 입력, 오른쪽에 "세(만 나이)". 15~39 밖은 막음 |
| 거주지 | 서울 / 서울 외 토글. 서울 선택 시 자치구 드롭다운(선택) |
| 현재 상태 | 5개 선택 버튼 중 하나 (재학, 휴학, 졸업예정(마지막 학기), 졸업 후 구직, 재직) |
| 관심 분야 | 6개 칩 복수 선택 (장학·교육, 생활비, 취업·훈련, 교통·통신·문화, 주거, 전체). "전체" 선택 시 나머지 해제 |
| 가구 소득 | 5개 선택 버튼, 기본 "잘 모르겠어요". 보조 문구 "몰라도 괜찮아요. 소득 기준이 있는 제도는 조건을 알려드려요." |
| 개인정보 안내 | "입력한 정보는 맞춤 안내를 위해 AI 모델로 전송되며 저장되지 않아요." |
| 시작 버튼 | "시작하기". 필수 4개가 채워지기 전엔 비활성 |

필수 4개는 나이, 거주지, 현재 상태, 관심 분야다. 자치구와 가구 소득은 비워도 넘어간다.

### 3-3. 홈 (첫 질문)

| 구성 요소 | 명세 |
| --- | --- |
| 입력창 | 화면 중앙, 안내 문구 "지금 상황이나 필요한 걸 편하게 말해 주세요" |
| 예시 칩 1 | "방학 동안 생활비 지원 받을 수 있는 거 있어?" |
| 예시 칩 2 | "취업 준비하는데 도움 되는 제도 알려줘" |
| 예시 칩 3 | "자취 시작했는데 월세 지원 있어?" |
| 예시 칩 4 | "교통비 아낄 수 있는 방법 있을까?" |
| 바로 찾아보기 | 입력 없이 폼 정보만으로 결과 보기 |

칩을 누르면 그 문장이 바로 전송된다. 입력창에 넣어두고 다시 누르게 하지 않는다.

### 3-4. 대화 결과 화면

| 구성 요소 | 명세 |
| --- | --- |
| 사용자 메시지 | 오른쪽 말풍선 |
| 진행 단계 | 답변 위 한 줄 "정책 찾는 중 → 조건 확인 중 → 정리 중". 현재 단계 강조, 완료 단계 체크 |
| 정책 카드 묶음 | 답변 위에 가로 스크롤(모바일) 또는 2열 그리드(데스크톱). 최대 5개 |
| 답변 본문 | 스트리밍으로 문장 단위로 붙임(글자 단위 아님). 각주 번호는 위첨자 버튼 |
| 후속 질문 | 답변 아래 카드 형태. 질문 한 줄, 이유 한 줄(작은 글씨), 선택지 버튼, "직접 입력", "건너뛰기" |
| 관련 질문 칩 (P1) | 맨 아래 2~3개 |
| 접힌 영역 | "조건이 맞지 않을 수 있는 제도 n개" 접기. 펼치면 `unlikely` 카드 |

카드가 답변보다 먼저 나오는 순서를 지킨다. 결과를 먼저 보여주고 설명이 따라붙는 구조다.

### 3-5. 정책 카드

| 구성 요소 | 명세 |
| --- | --- |
| 상태 배지 | 아이콘 + 문구. 색은 보조 수단 |
| 제목, 기관 | 제목 2줄까지, 넘치면 말줄임 |
| 혜택 한 줄 | 혜택 요약 첫 문장 |
| 마감 배지 | 마감 임박 D-n / D-n / 오늘 마감 / 상시 접수 / 접수 예정 (시작일) |
| 조건부 문장 | `check`일 때만. 카드 하단 작은 글씨 |
| 출처 줄 | "출처: 기관명 · 확인일 2026.09.19" |
| 갱신 표시 | 상태가 바뀌면 배지가 0.3초 동안 부드럽게 바뀌고 "업데이트됨" 표시 2초 |

### 3-6. 각주 팝오버

| 구성 요소 | 명세 |
| --- | --- |
| 발췌문 | 인용 표시로 감싼 공고 원문 조각 |
| 기관명 | 조건 근거의 출처 기관 |
| 확인일 | 팀이 원문을 마지막으로 확인한 날짜 |
| 원문 링크 | "공고 원문 보기" |
| 닫기 | 바깥을 누르거나 ESC |

### 3-7. 정책 상세 패널

| 순서 | 구역 | 명세 |
| --- | --- | --- |
| 1 | 머리 | 제목, 기관, 상태 배지, 마감 배지 |
| 2 | 조건 판정표 | 조건마다 한 줄 — 결과 아이콘, 조건 요약, 각주 버튼. 순서는 미충족 → 미확인 → 충족 |
| 3 | 조건부 문장 | `check`일 때 |
| 4 | 혜택 | 전체 |
| 5 | 신청 기간 | 시작일 ~ 마감일, D-day |
| 6 | 체크리스트 | 3-8 |
| 7 | 출처 | 공고 원문 링크, 확인일, 재확인 필요 표시(해당 시) |
| 8 | 고정 안내 | "최종 신청 전 공식 공고에서 다시 확인하세요" |

### 3-8. 체크리스트

| 항목 | 명세 |
| --- | --- |
| 순서 | 서류 항목 먼저, 신청 단계 다음 |
| 각 항목 | 체크 박스 |
| 마지막 항목 | "공식 신청 페이지로 이동" 버튼 |
| 유지 범위 | 체크 상태는 세션 동안만 유지 |

### 3-9. 프로필 요약 바

| 항목 | 명세 |
| --- | --- |
| 표시 형태 | "만 23세 · 서울 · 재학 · 소득 모름" |
| 누르면 | 폼과 같은 항목을 수정하는 작은 창 |
| 대화로 바뀌면 | 바뀐 항목이 2초간 강조 |
| 대화 안내 | "휴학으로 바꿨어요" 같은 안내가 대화에 한 줄 들어감 |

### 3-10. 스트리밍 이벤트별 화면 반응

| 이벤트 | 화면 반응 |
| --- | --- |
| `status` | 진행 단계 갱신 |
| `profile_update` | 프로필 바 갱신 + 대화에 안내 한 줄 |
| `policies` | 카드 묶음 갱신. 기존 카드는 자리 유지하고 상태만 바뀜, 새 카드는 뒤에 추가 |
| `answer_delta` | 답변 본문에 이어 붙임 |
| `footnotes` | 각주 번호를 발췌와 연결 |
| `followup` | 후속 질문 카드 표시 |
| `related` | 관련 질문 칩 표시 |
| `error` | 카드 유지 + 오류 문구 + 다시 시도 |
| `done` | 진행 단계 숨김, 입력창 활성 |

답변 생성 중에도 입력창은 비활성으로 두고, 후속 질문 버튼은 `done` 이후에만 누를 수 있다.

## 4. 로딩·빈 상태·오류

| 상황 | 화면 |
| --- | --- |
| 첫 결과 대기 | 카드 자리에 뼈대(스켈레톤) 3개 |
| 결과 없음 | "지금 조건으로는 찾은 제도가 없어요" + 넓히는 방법 2개(관심 분야 "전체"로, 거주지 확인) + 온통청년 링크 |
| AI 설명 실패 | 카드는 그대로 두고 "설명을 불러오지 못했어요. 카드에서 조건을 확인해 주세요" + 다시 시도 버튼 |
| 연결 끊김 | "연결이 끊겼어요" + 다시 시도 |
| 세션 만료 | "시간이 지나 처음부터 다시 시작할게요" + 온보딩으로 |
| 민감정보 입력 | 입력창 아래 "주민등록번호나 계좌번호는 입력하지 않아도 돼요" |
| 입력 오류 | "입력한 정보를 다시 확인해 주세요" |

AI가 실패해도 규칙 기반 카드는 이미 화면에 있다. 카드를 지우는 오류 화면은 만들지 않는다.

## 5. 접근성

| 항목 | 기준 |
| --- | --- |
| 상태 구분 | 상태 배지는 아이콘 + 문구. 색만으로 구분 금지 |
| 대비와 글자 크기 | 본문 대비 4.5:1 이상, 모바일 본문 14px 이상 |
| 키보드 | 모든 버튼·칩·카드에 포커스 표시, Tab 순서는 화면 읽는 순서와 같게 |
| 스트리밍 | **답변 본문을 자동 낭독 대상으로 두지 않는다.** 진행 단계와 완료만 공손한 라이브 리전에서 짧게 알린다. 문장이 붙을 때마다 낭독이 끊기면 읽을 수 없는 화면이 된다 |
| 라이브 리전 | 상태 영역을 처음부터 화면에 둔다. 갱신 후에 만들면 알림이 발생하지 않는다 |
| 낭독을 끊는 것 | 오류에만. 나머지는 모두 공손하게 |
| 카드 갱신 알림 | 카드마다 알리지 않고 한 번만 |
| 각주 활성 시점 | 각주 번호는 답변 완료 후 활성화한다. 누를 수 있어 보이는데 반응하지 않는 상태를 두지 않는다 |
| 근거 | `../docs/research/03-streaming-ux-and-latency.md` 4절, `../docs/08-risks-privacy-a11y.md` |
| 이름 | 각주 버튼에 "근거 1번 보기" 같은 읽을 수 있는 이름 |

## 6. 시각 방향

| 항목 | 방향 |
| --- | --- |
| 톤 | 차분하고 신뢰감 있게. 흰 배경, 본문은 짙은 회색, 강조색 1개 |
| 상태 색 | `likely` 초록 계열, `check` 주황 계열, `unlikely` 회색 계열. 빨강은 마감 임박에만 |
| 카드 | 모서리 12px, 그림자 약하게, 각주 번호는 강조색 원형 |
| 본문 | 답변 가독성 최우선, 줄간격 넉넉하게 |

## 8. 완료 기준

- [ ] 키보드만으로 폼 제출과 카드 열기 가능

## 9. 배포 전제: S3 정적 호스팅

캠프에서 **S3**를 준다. 프론트는 S3에 정적 파일로 올린다. 이 제약이 프레임워크 선택과 설계를 결정한다.

| 제약 | 무엇을 뜻하는가 | 어떻게 대응하는가 |
| --- | --- | --- |
| 정적 파일만 올라간다 | 서버 사이드 렌더링을 쓸 수 없다. 빌드 결과가 파일 묶음이어야 한다 | 단일 페이지 앱으로 만든다. 서버 렌더가 기본인 프레임워크를 고르면 정적 내보내기가 되는지 먼저 확인한다 |
| API가 다른 오리진에 있다 | 브라우저가 교차 출처 요청으로 본다. 스트리밍 응답도 같다 | 백엔드B가 서버에서 프론트 주소를 허용 오리진으로 등록한다. 10:30에 양쪽 주소를 맞춘다 |
| 페이지와 API의 프로토콜이 달라지면 막힌다 | 페이지가 보안 연결인데 API가 아니면 브라우저가 요청을 차단한다 | 10:30에 백엔드B와 프로토콜을 맞춘다. 맞지 않으면 배포 전에 드러나야 한다 |
| API 주소를 어딘가에 넣어야 한다 | 빌드할 때 주소를 박으면 주소가 바뀔 때마다 다시 빌드해야 한다 | 주소를 담은 작은 설정 파일을 따로 두고 실행 중에 읽는다. 주소가 바뀌어도 그 파일만 다시 올린다 |
| 다시 올려도 예전 화면이 보일 수 있다 | 브라우저나 중간 캐시가 시작 파일을 들고 있는 경우 | 시작 파일은 캐시하지 않게, 이름에 해시가 붙는 자원은 길게 캐시하도록 설정한다. 데모 전에 다른 브라우저로 한 번 열어 확인한다 |
| 주소 경로를 여러 개 쓰면 새로고침이 깨질 수 있다 | 정적 호스팅은 없는 경로를 찾지 못한다 | 화면 전환을 경로로 나누지 않는다. 온보딩 → 홈 → 대화는 한 화면 안의 상태로 다룬다. 이건 원래 설계와도 맞는다 |

**데모 직전 재배포는 하지 않는다.** 14:30 기능 동결 이후에는 버그 수정만 올리고, 올린 뒤에는 반드시 배포 주소에서 데모 경로를 한 번 통과시킨다.
