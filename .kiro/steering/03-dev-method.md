# 개발 방식 · 자문자답 사전 오류 점검

사용자가 지정한 작업 방식이다. 모든 구현 작업에 적용한다.

## 원칙

**코드를 쓰기 전에, 그 코드가 깨질 시나리오를 먼저 찾는다.** 돌아가는 걸 만들고 나서 버그를 잡는 게 아니라, 만들기 전에 "이게 왜 안 될까"를 자문자답해서 미리 막는다.

## 구현 단위마다 거치는 순서

1. **사전 점검 (자문자답)** — 이 모듈이 실패할 경로를 스스로 묻고 답한다. 최소한 아래를 훑는다.
   - 입력 데이터가 예상과 다른 형태로 올 경우 (인코딩, 공백, 빈 값, 타입, 길이 초과)
   - 외부 호출이 느리거나 실패할 경우 (타임아웃, rate limit, 형식 깨짐)
   - 다른 역할과의 계약이 어긋날 경우 (필드명, 값 범위, 누락)
   - 경계값 (0개, 1개, 최대치, 딱 기준선)
   - 실패했을 때 사용자 화면이 어떻게 되는지
2. **막을 것과 감수할 것을 나눈다** — 전부 방어하면 시간이 없다. 데모를 깨뜨리는 것만 막고, 나머지는 기록만 남긴다.
3. **구현** — 위에서 정한 방어만 넣는다. 스펙에 없는 기능이나 추상화를 덧붙이지 않는다.
4. **검증** — 사전 점검에서 찾은 시나리오를 실제로 실행해 확인한다. 정상 경로만 돌려보고 "됐다"고 하지 않는다.
5. **보고** — 확인한 것과 확인하지 못한 것을 구분해서 말한다. 명령이 에러 없이 끝난 것은 성공의 증거가 아니다.

## 보고 규칙

- 검증한 것과 검증 못 한 것을 명확히 구분한다. 추측을 사실처럼 말하지 않는다.
- 문제를 발견하면 숨기거나 나중으로 미루지 않고 바로 말한다.
- 스펙 자체에 모순이나 빈 구멍이 있으면 임의로 메우지 않고 알린다. 특히 다른 역할과의 인터페이스(02-roles-common 1-4)에 걸린 문제는 백엔드B에게 알려야 하는 사항이라고 명시한다.

## 이 프로젝트에서 특히 조심할 것

해커톤 당일이라 시간이 짧다. 그래서 다음을 우선한다.

| 우선 | 이유 |
| --- | --- |
| 데모 경로(PRD 15장)를 깨뜨리는 문제 | 발표가 안 됨 |
| 인용 검증이 전부 실패하는 문제 | 모든 조건이 미확인 → 카드가 전부 check → 핵심 가치가 화면에서 사라짐 |
| /chat 20초 상한 초과 | 발표 중 정적 |
| 미충족 오판 | 완료 기준이 0건. 사용자에게 "안 된다"고 잘못 말하는 게 가장 나쁨 |

반대로 다음은 시간이 남을 때만 손댄다: 넓은 입력 검증, 리팩터링, 테스트 커버리지 확대, 스펙에 없는 예외 처리.

## git 작업 규칙

**`dev` 브랜치에서 작업하고 `dev`에 푸시한다.** 이게 팀 통합 지점이다.

- 역할별 기능 브랜치를 새로 만들지 않는다. 갈래가 늘면 통합할 때 손해다
- PR을 만들지 않는다. `dev`에 바로 올린다
- `main`은 건드리지 않는다. 백엔드B가 통합 시점에 처리한다
- 커밋 전에 테스트를 돌린다: `python3 -m unittest discover -s tests -t .`
- 푸시하기 전에 `git pull origin dev`로 팀원 작업을 먼저 받는다
