# 작업 방식 (자동 적용)

> 이 파일은 저장소를 클론한 모든 팀원의 Kiro에 자동으로 적용된다.
> 근거는 `docs/research/` 네 편에 있다. 규칙만 여기 두고, 왜 그런지는 그 문서를 본다.

## 1. 추측하지 말고 물어본다

문서에 답이 없는데 결정이 필요하면 **멈추고 사용자에게 물어본다.** 그럴듯한 값을 채워 넣지 않는다.
하루짜리 일정에서 잘못된 가정으로 30분을 쓰는 것이 질문 하나보다 훨씬 비싸다.

### 반드시 물어봐야 하는 것

| 상황 | 왜 물어야 하는가 |
| --- | --- |
| 프로필 항목이나 허용 값을 새로 만들어야 할 때 | 다섯 명이 같은 값을 써야 한다. 혼자 늘리면 통합에서 깨진다 |
| 고정 값(판정 상태, 조건 결과, 의도, 진행 단계)에 없는 값이 필요할 때 | 같은 이유 |
| API 경로, 요청·응답 항목, 스트리밍 이벤트를 추가하거나 바꿔야 할 때 | 10:30 이후 변경은 백엔드B 경유다 |
| 사용자에게 보이는 새 문구가 필요할 때 | 문구는 표에서 관리한다. 코드에 바로 쓰지 않는다 |
| 자기 소유 폴더 밖의 파일을 고쳐야 할 때 | 소유자가 모르는 변경이 생긴다 |
| 라이브러리나 패키지를 새로 추가해야 할 때 | 의존성은 최소로 유지하고 버전을 고정한다 |
| 정책 데이터의 값이 공고와 다르거나 비어 있을 때 | 데이터 판단은 백엔드A 몫이다 |
| 문서끼리 서로 다른 말을 할 때 | 문서를 먼저 고쳐야 한다. 코드로 한쪽을 따라가면 다른 쪽이 틀린 채로 남는다 |
| 요구사항을 만족시키려면 다른 요구사항을 깨야 할 때 | 우선순위 판단이 필요하다 |

### 물어보는 방법

- 한 번에 하나씩, 선택지를 함께 제시한다. "A로 할까요, B로 할까요? 문서에는 없습니다."
- 무엇을 이미 확인했는지 밝힌다. 어느 문서를 읽었고 거기에 없었다고 말한다.
- 막힌 동안 할 수 있는 다른 작업이 있으면 그것부터 하고, 질문을 모아 한 번에 묻는다.

### 물어보지 않아도 되는 것

변수 이름, 파일 배치, 서식, 동등한 방법 중 하나를 고르는 일. 합리적인 쪽을 고르고 그렇게 했다고 한 줄 알린다.

## 2. 구현 전에 읽는다

작업을 시작하기 전에 관련 문서를 읽는다. 이미 정해진 값을 새로 만들지 않는다.

| 무엇을 만들든 | 먼저 볼 문서 |
| --- | --- |
| 프로필·판정·마감·정렬을 다루는 모든 것 | `docs/01-glossary-profile.md` |
| 서버와 주고받는 모든 것 | `docs/03-api-contract.md` |
| 정책 데이터를 다루는 모든 것 | `docs/04-data-schema.md` |
| 다른 역할과 접하는 모든 것 | `docs/05-interfaces.md` |
| 자기 역할의 상세 | 자기 폴더 `README.md` |

KIRO Spec에 넣을 때는 **필요한 문서만** 넣는다. 전체를 다 넣으면 중간 내용이 묻힌다
(근거: `docs/research/01-ai-assisted-dev-quality.md` 4절).

## 3. 검증 없이 완료라고 말하지 않는다

"구현했다"와 "동작한다"는 다르다. 통제 실험에서 체감과 실측이 반대로 나온 사례가 있다
(근거: `docs/research/01-ai-assisted-dev-quality.md` 2절).

| 무엇을 만들었으면 | 무엇으로 확인하는가 |
| --- | --- |
| 화면 | 실제로 열어서 클릭해 본다. 키보드만으로도 해 본다 |
| API | 요청을 보내 응답을 본다. 오류 경로도 한 번 본다 |
| 규칙 판정 | 대표 프로필 P1~P5로 돌려 기대 결과와 비교한다 |
| 메시지 해석·답변 | 해석 테스트 10개와 C1~C8을 돌린다 |
| 예외 조건 판정 | J1~J8을 돌린다. 특히 미충족 오판이 0건인지 |
| 프롬프트를 고쳤을 때 | 자기 담당 케이스를 **다시** 돌린다. 통과 못 하면 되돌린다 |

## 4. 되돌릴 수 있게 만든다

- 동작하는 지점마다 커밋한다. 커밋 하나에 관심사 하나.
- 여러 역할 폴더를 한 커밋에 섞지 않는다.
- 전체 추가 대신 파일을 지정해 스테이징한다.
- 큰 변경을 하기 전에 지금 상태를 커밋해 둔다.

## 5. AI가 쓴 코드를 그대로 믿지 않는다

실증 연구에서 생성 코드의 취약 비율이 높게 나온다
(근거: `docs/research/01-ai-assisted-dev-quality.md` 1절).

| 자리 | 무엇을 해야 하는가 |
| --- | --- |
| 민감정보 마스킹 (FR15) | 사람이 직접 읽는다. 가린 값이 모델 요청과 기록 어디에도 남지 않는지 확인 |
| 입력 검증 | 허용 값 밖 입력이 통과하지 않는지 확인 |
| 교차 출처 설정 | 와일드카드로 열지 않는다. 프론트 주소만 허용 |
| 외부 호출 | 시간 제한과 실패 처리가 있는지 확인 |
| 새 패키지 | 실제로 존재하는지, 최근에 배포됐는지 확인하고 버전을 고정한다 |

패키지 이름을 모델이 만들어내는 일이 실제로 관찰된다. 낯선 이름은 반드시 레지스트리에서 확인한다.

## 6. 서브 에이전트를 병렬로 쓸 때

각자 자기 작업을 여러 에이전트로 쪼개도 된다. 단 기준이 있다
(근거: `docs/research/01-ai-assisted-dev-quality.md` "에이전트를 병렬로 쓸 때의 규칙").

| 나눠도 되는 것 | 나누면 위험한 것 |
| --- | --- |
| 서로 다른 파일의 독립 작업 | 같은 파일을 동시에 고치는 작업 |
| 화면 단위 구현 (카드, 상세 패널, 팝오버) | 전역 상태 구조 설계 |
| 정책 데이터 수집·검수 (건별 분할) | 공용 타입·인터페이스 정의 |
| 평가 케이스 작성, 문서 정리, 조사 | 판정·정렬 규칙처럼 여러 모듈이 공유하는 규칙 |
| 서로 다른 오류 경로 처리 | 커밋과 머지 |

**병렬로 돌릴 때 각 에이전트에게 반드시 같이 주는 것**

1. 건드려도 되는 파일 경로와 건드리면 안 되는 경로
2. 고정 값 목록과 필드 이름 규칙 (`docs/01-glossary-profile.md`, `CONTRIBUTING.md` 7장)
3. 그 작업의 완료 기준
4. 모르면 만들지 말고 멈추라는 지시

이걸 주지 않으면 각 에이전트가 자기 가정으로 채운다. 그게 병렬 작업이 깨지는 가장 흔한 이유다.

**끝난 뒤 확인할 것**: 같은 개념에 다른 이름이 붙지 않았는지, 인터페이스 문서와 어긋나지 않는지.

## 7. 범위를 늘리지 않는다

- 요청받은 것만 만든다. 없던 기능, 없던 설정, 없던 추상화를 추가하지 않는다.
- 버그 하나를 고치면서 주변 코드를 정리하지 않는다.
- 남의 코드를 지나가며 리팩터링하지 않는다.
- 시간이 밀리면 `docs/00-overview.md`의 "빼는 순서"를 따른다. 스스로 새 순서를 만들지 않는다.
- **끝까지 지키는 것은 원문 각주, 후속 질문, 즉시 결과 세 개다.**

## 8. 시각별 기준

| 시각 | 여기까지 안 됐으면 범위를 줄인다 |
| --- | --- |
| 12:00 | 규칙 판정이 돌고, 프론트가 목업으로 카드를 그리고, 세션 생성이 응답한다. 스트리밍이 교차 출처에서 뚫리는지 확인 |
| 14:00 | 데모 경로가 끝까지 한 번 통과한다 (각주·후속 질문·상세 포함) |
| 14:30 | 기능 동결. 이후 버그 수정만 |

13:00~14:30 사이에 **AI 호출을 일부러 끊고 카드가 남는지** 한 번은 확인한다.
확인하지 않으면 폴백은 설계로만 존재하는 것이다.
