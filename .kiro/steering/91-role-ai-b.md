## 6-1. 판정 대상

| 구분 | 내용 |
| --- | --- |
| 판정하는 것 | 정책의 `exceptions_text`에 있는 **문장형 조건만** |
| 판정하지 않는 것 | 나이, 지역, 신분, 소득 %, 추가 항목, 마감 — 백엔드A 규칙 엔진 몫. **겹쳐도 다시 판정하지 않는다** |
| 판정 단위 | 정책 하나씩, 후보 정책들을 동시에 |

## 6-2. 판정 기준

| 결과 | 기준 | 예 |
| --- | --- | --- |
| 충족 | 프로필에 명시된 값으로 조건을 만족하는 것이 분명함 | "재학생 또는 휴학생" + 사용자 휴학 |
| 미충족 | 프로필에 명시된 값이 제외 대상에 분명히 해당함 | "휴학생 제외" + 사용자 휴학 |
| 미확인 | 프로필에 해당 정보가 없음, 원문 표현이 모호함("등", "그 밖에"), 판단에 외부 정보가 필요함 | "타 지원금 수혜자 제외" + 정보 없음 |

핵심 원칙:
- **미충족은 명시된 정보로 분명할 때만.** 조금이라도 애매하면 미확인.
- 사용자가 말하지 않은 것을 상식으로 추정하지 않는다. (금지 예: 대학생이니 소득이 낮을 것이다)
- 미확인이면 필요한 정보를 02-roles-common 1-2 추가 항목 중 하나로 지정한다. 해당 항목이 없으면 `"공고 확인 필요"`로 둔다.

## 6-3. 판정 결과 항목

| 항목 | 기준 |
| --- | --- |
| 조건 요약 | 20자 이내 명사형. 예: "타 청년 지원금 중복 불가" |
| 결과 | 충족, 미충족, 미확인 |
| 발췌 | 원문의 연속된 부분 그대로, **10~150자**, 조건당 1개 |
| 필요한 추가 항목 | 미확인일 때만. 1-2 추가 항목 이름 또는 "공고 확인 필요" |

이 형식은 백엔드B에 넘기는 인터페이스다. 09:30에 확정하면 변경하지 않는다.

## 6-4. 인용 검증 (가장 중요한 가드레일)

구현: `ai/citation/` · 테스트: `tests/test_citation.py`

| 단계 | 기준 |
| --- | --- |
| 정리 | 아래 정규화 규칙을 발췌와 `raw_text`에 똑같이 적용 |
| 대조 | 정리된 발췌가 정리된 `raw_text` 안에 그대로 들어 있는지 확인 |
| 통과 | **원문에서 되찾은 구간으로 발췌를 교체**한 뒤 그대로 둠 |
| 실패 | 해당 조건을 **미확인으로 바꾸고**, 발췌와 조건 요약을 화면에 내보내지 않음. **제거 건수 기록** |

- 규칙 조건의 근거 문장(백엔드A가 스프레드시트에 채운 것)도 같은 방식으로 한 번 검증한다.
- **검증은 AI가 아니라 로직으로 한다.** LLM에 재확인을 맡기지 않는다.

### 정규화 규칙 (macOS · Windows 혼용 대응)

원래 규칙("줄바꿈·연속 공백을 공백 하나로, 앞뒤 공백 제거")만으로는 **전건 실패한다.** 사람 눈에 같아 보이는 문자열이 코드에서 다른 경우가 세 층으로 존재한다. 순서대로 적용한다.

| 순서 | 처리 | 막는 문제 |
| --- | --- | --- |
| 1 | 유니코드 **NFC** 정규화 | macOS는 한글을 자모 분해형(NFD)으로 넘기는 경로가 많다(파일명, 클립보드, 일부 브라우저 복사). Windows는 완성형(NFC). "휴학"이 NFC 2자 / NFD 4자가 되어 포함 검사가 **무조건** 실패한다 |
| 2 | 제로폭 문자 제거 — `U+FEFF`(BOM), `U+200B/C/D`, `U+2060`, `U+00AD` | Windows Excel의 UTF-8 저장은 선두에 BOM을 붙인다. 웹 공고 복사에는 제로폭 공백이 섞인다 |
| 3 | 공백류를 공백 하나로 — `\t \n \r \v \f`, `U+00A0`(NBSP), `U+3000`(전각), `U+2000~200A`, `U+202F`, `U+205F`, `U+1680` | CRLF/LF 차이, HTML `&nbsp;` 복붙, 한글 공고의 전각 공백 들여쓰기 |
| 4 | 연속 공백을 하나로 접기 | AI가 줄바꿈을 공백으로 바꿔 인용하는 경우 |
| 5 | 앞뒤 공백 제거 | |

**문장 부호는 건드리지 않는다.** 대시·따옴표 종류를 통일하면 근거의 내용을 바꾸게 된다. 정규화는 보이지 않는 차이만 흡수한다.

### 원문 되찾기 (원문 우선 원칙)

정규화는 비교에만 쓴다. 검증을 통과하면 **정규화 위치를 원문 위치로 되돌려 원문에서 실제 구간을 꺼내 발췌를 교체한다.** AI가 공백을 다르게 쓴 발췌를 보내도 사용자가 보는 문장은 항상 공고 원문 쪽이다.

### 발췌 길이 처리

- 10자 미만: 실패(`too_short`). 근거로 쓸 수 없고 아무 데나 매칭된다
- 150자 초과: **실패로 보지 않고 앞 150자로 자른 뒤 검증.** 포함된 문자열의 앞부분도 포함되므로 안전하고, 길이 때문에 맞는 판정을 버리지 않는다. 자른 뒤에도 원문에 없으면 그대로 실패

### 실패 사유 코드 (지표용)

`empty_excerpt` · `empty_raw` · `too_short` · `not_found`

### git 계층 1차 방어

`.gitattributes`가 저장소 안 모든 텍스트를 LF로 강제한다(`* text=auto eol=lf`). Windows에서 커밋한 CRLF가 `raw_text`에 섞이는 걸 막는다. 단 스프레드시트 붙여넣기나 API 응답은 git을 거치지 않으므로, 런타임 정규화가 최종 방어선이다. 둘 다 있어야 한다.

### 데이터 불변식: `exceptions_text` ⊂ `raw_text`

판정 입력은 `exceptions_text`인데 대조 대상은 `raw_text`다. 백엔드A가 예외 문장을 요약하거나 고쳐 적었으면 그 정책의 **모든 발췌가 `not_found`로 떨어진다.** 정책 데이터를 적재할 때 `raw_text_covers()`로 미리 걸러야 한다. **백엔드A·B에 공유해야 하는 사항.**

## 6-5. 조건부 문장 (고정 형식, AI가 자유 작성 금지)

| 미확인 원인 | 문장 형태 |
| --- | --- |
| 소득 | 가구 소득이 기준 중위소득 n% 이하라면 신청 가능해요 |
| 추가 항목 | (항목)이 (값)이라면 신청 가능해요 |
| 예외 조건 | (조건 요약)에 해당하지 않는다면 신청 가능해요 |
| 미확인 2개 이상 | 가장 위의 하나만 문장으로, 나머지는 "외 n개 조건 확인 필요" |

위 형식에 값만 넣는다.

| 번호 | 예외 문장 유형 | 프로필 | 기대 결과 |

| J1 | 휴학생 제외 | 휴학 | 미충족 |

| J5 | 최근 n년 내 동일 사업 참여자 제외 | 정보 없음 | 미확인, 공고 확인 필요 |
| J6 | 학점 기준 이상 | 성적 모름 | 미확인, 직전 학기 성적 |
| J7 | "기타 부적격자" 같은 모호 문장 | 아무 프로필 | 미확인, 공고 확인 필요 |
| J8 | 서울 소재 대학 재학생 | 서울 거주, 학교 소재 모름 | 미확인, 공고 확인 필요 |

### 상태: 실제 공고 문장으로 교체 필요

8건 전부 아직 실제 문장이 아니다. 공고의 표현 방식을 따라 쓴 대체물이 들어 있고, `source_url`이 `None`인 것이 그 표시다. `python3 -m ai.judgment`로 현황을 확인한다.

**정책 스프레드시트가 있어야 채울 수 있다.** 채우는 방법은 `exceptions_text`를 공고에서 복사해 붙이고, 그 문장을 포함한 자격·제외 대상 단락을 `raw_text`에 그대로 넣고, `source_url`을 기입하는 것이다. 다듬거나 요약하면 인용 검증이 깨진다.

실제 문장이 필요한 이유는 공고 문장이 예상보다 지저분하기 때문이다. 괄호 주석, 표를 풀어 쓴 줄, "등"·"그 밖에" 같은 열린 표현이 섞인다. 깔끔한 문장으로만 평가하면 본선에서 다르게 동작한다.

### 채점 방식

**판정기 출력을 그대로 채점하지 않는다. 인용 검증을 통과한 뒤의 결과를 채점한다.** 판정이 맞아도 발췌가 원문에 없으면 실제로는 미확인으로 강등되므로, 검증 전 출력으로 채점하면 본선 동작과 어긋난다.

조건이 여러 개면 가장 심각한 것(미충족 > 미확인 > 충족)을 대표로 삼는다. 판정 상태 계산(1-3)에서 미충족이 우선하는 것과 같은 방향이라 실제 카드 상태와 일치한다.

| 집계 항목 | 뜻 |
| --- | --- |
| 통과 | 결과와 필요한 추가 항목이 모두 기대대로 |
| **미충족 오판** | 기대가 미충족이 아닌데 미충족으로 판정. **완료 기준 0건.** 사용자에게 잘못 "안 된다"고 말하는 경우라 가장 위험 |
| 안전한 쪽 오차 | 미충족인데 미확인으로 봄. 틀렸지만 위험하지 않음 |
| 결과만 맞음 | 결과는 맞고 필요한 추가 항목이 틀림 |
| 인용 검증 제거 | 발췌가 원문에 없어 제거된 건수 |

판정기는 `judge(exceptions_text, profile, raw_text) -> list[조건]` 형태로 주입한다. LLM이 정해지기 전에도 채점기를 검증할 수 있게 했다.

### 근거 없는 조건 점검표 [사전 준비]

정책별로 원문에 있는 조건 목록을 미리 적어 두고, 본선 당일 화면에 나온 조건이 목록에 없으면 1건으로 센다.

인용 검증과 목적이 다르므로 둘 다 필요하다. 인용 검증은 "이 문장이 원문에 있는가"만 본다. 원문에 있는 문장을 **엉뚱한 조건으로 갖다 붙인** 경우는 통과시킨다. 점검표는 그걸 잡는다.
